## 2. Способы лечения — с ценой, а не только с устройством

Общее для всех: **бакет `mugam-club.firebasestorage.app` лежит в
`US-EAST1`** (`gsutil ls -L -b`), а функции — в `europe-west3`
(`FUNCTIONS_REGION`, `functions/src/index.ts:70`), кроме хранилищного
триггера, который нарочно в `us-east1` (строка 1242). **Любая функция в
пути раздачи обязана стоять в `us-east1`**, иначе байты пересекут океан
дважды.

**Живых трубок — четыре по push-токенам** (4 токена у 4 учёток из 12,
замер 15.09), из них две заведомо владельца. Это делает цену «сломаются
старые сборки» в этом проекте **много меньше обычной** — но не нулевой.

### а) Раздача через облачную функцию с проверкой прав

| | |
|---|---|
| **Устройство** | функция принимает путь, сама проверяет права по Firestore, отдаёт байты |
| **Мест в клиенте** | все 11 адресов + все читатели URL на показе |
| **Деплой функций** | **да**, и новую функцию в `us-east1` |
| **Старые сборки** | **перестают показывать медиа совсем**, если убрать URL из документов; работают, если URL оставить — но тогда починки нет |
| **Деньги** | вызов на **каждый** показ + исходящий трафик **дважды** (бакет → функция бесплатно внутри региона, функция → телефон платно). Сегодня в бакете **102,39 МиБ** (`gsutil du -s -h`) |
| **Скорость** | **медленнее всегда.** Цена названа замером, а не оценкой: **N229** — холодный старт функции в этом проекте **4,00 с**, тёплые вызовы 0,85–1,28 с. Это ляжет на **каждое** открытие картинки |

**Вывод по (а): для медиа переписки неприемлемо по скорости** — 21 картинка
и 15 видео в проде превратятся в 36 ожиданий по секунде-четыре.

### б) Подписанные ссылки с коротким сроком (signed URL)

| | |
|---|---|
| **Устройство** | функция проверяет права и выдаёт `getSignedUrl({action:'read', expires})`; байты идут из бакета напрямую |
| **Мест в клиенте** | все 11 + читатели: URL теперь **нельзя хранить** в документе, он протухает |
| **Деплой функций** | **да**, одна функция. **Плюс права на подпись** (`iam.serviceAccountTokenCreator` / SignBlob) — **у нас не проверено, есть ли они** (I50) |
| **Старые сборки** | то же, что у (а) |
| **Деньги** | один вызов на показ (дёшево), трафик — как сегодня, один раз |
| **Скорость** | один вызов **перед** началом: тёплый ≈1 с, холодный до 4 с (N229). Лучше (а) на величину самих байтов, но ожидание перед каждым показом остаётся |

**(в) — не починка, а зачистка.** В одиночку она только ломает. Смысл
появляется **после** (а)/(б)/(г1), когда клиент перестал зависеть от токена.

### г) Что ещё есть — четыре способа, которых в вопросе не было

#### г1. Читать файл SDK-ом, а не по ссылке — **и это же чинит N233**

`firebase_storage` умеет `ref.writeToFile(File)` и `ref.getData()`
(проверено в самом пакете: `firebase_storage-13.4.3/lib/src/reference.dart`,
строки 217 и 101). Это **чтение по правилам, под учёткой человека**:
токен не нужен вовсе. В документе лежит **путь**, а не URL.

| | |
|---|---|
| **Мест в клиенте** | 11 адресов, но **делится по одному**: можно начать с причины выхода и не трогать остальные |
| **Деплой функций** | **НЕ НУЖЕН ВОВСЕ** — единственный способ из всех без выкладки |
| **Старые сборки** | молчат, если поле подменить. Лечится переходом: писать **оба** поля, читать путь, когда он есть |
| **Деньги** | как сегодня (прямое скачивание), **дешевле на повторах** — скачанное кладётся в файл и живёт |
| **Скорость** | первый раз — как сегодня; **второй и дальше — мгновенно**, потому что кэш появляется тем же заходом (N233) |

#### г2. Сузить само правило чтения — одна строка

`event_leave_notes`: с «владелец ∪ **весь состав**» до «владелец ∪ **сам
загрузивший**». Загрузивший обязан остаться: `uploadLeaveNoteVoice` зовёт
`getDownloadURL()` **сразу после** загрузки, а это чтение (та же
курица-и-яйцо, что описана у статусов в `storage.rules:117-135`).

Трогает **правила, а не клиент**; старые сборки не ломает; денег не стоит;
не замедляет ничего. **Токен не лечит вовсе** — сужает только законный круг.

#### г3. Не класть готовый URL в документ, а звать `getDownloadURL()` при показе

Токен остаётся вечным, но перестаёт **лежать** в поле, которое читает
состав: чтобы его добыть, надо иметь право чтения в хранилище. Половина
починки: добытый однажды токен всё равно вечен. Деплоя не требует.

#### г4. Признать группы 1 и 3 терпимыми и починить только группу 2

Самый дешёвый честный ход: решение владельца, записанное словами, вместо
работы. **Требует, чтобы обещание было названо вслух** — сейчас у фото
группы его нет (см. группу 3).

## 5. С чего бы я начал — и почему

**Решение за владельцем. Ниже — мой порядок и довод к каждому шагу.**

**Шаг 0 — то, что уже сделано этим разбором: назвать обещание вслух для
каждого из 11 адресов.** Без этого «нарушено ли» не проверяется ничем
(группа 3 — ровно такой случай).

**Шаг 1 — г2, сузить правило чтения причины выхода до «владелец ∪ сам
загрузивший».** Одна строка в `storage.rules`. **Почему первым:** это
единственный шаг, который **никак не может сломать живое** — правила
сужают, клиент не трогается, старые сборки не знают о нём вовсе. И он
чинит **половину разрыва между обещанием и правдой** — ту, что про
законный круг.

**Шаг 2 — г1, чтение SDK-ом для причины выхода, и только для неё.** Один
адрес, **четыре файла в проде**, необратимого ничего. **Почему вторым:**
он несёт **одну переменную** (I48) и заодно закрывает N233 — кэш
появляется сам собой. Если что-то пойдёт не так, видно сразу и на одном
месте.

**Шаг 3 — (в), отзыв токенов у четырёх файлов причин.** Только после
шага 2 и только по этим четырём: к тому времени клиент их не читает по
ссылке, а старые сборки на двух трубках обновляются нами же.

**Шаг 4 — решение владельца по группе 2 целиком** (переписка и статусы, 8
адресов). Здесь я бы **не спешил**: цена (а) и (б) — задержка на каждом
показе, замеренная N229 в секундах, а выигрыш — от угрозы, для которой у

## 6.1. Было и станет, рядом

**Нынешнее — `storage.rules:170-173`, выложено в проде:**

```
allow read: if isSignedIn() && (
  request.auth.uid == leaveEvent().ownerUid ||
  request.auth.uid in leaveEvent().get('musicians', [])
);
```

**Предлагаемое:**

```
allow read: if isSignedIn() && (
  request.auth.uid == uid ||
  request.auth.uid == leaveEvent().ownerUid
);
```

**Круг был:** владелец ∪ **любой из `musicians`** ∪ вышедший (он в составе,
потому и читал).
**Круг станет:** владелец ∪ **сам вышедший** (`{uid}` — это имя файла, то
есть чья это запись).

**Три решения внутри одной правки, названные отдельно, чтобы их не приняли
за оформление:**

1. **`musicians` из чтения уходит совсем** — это и есть сужение;
2. **`request.auth.uid == uid` стоит ПЕРВЫМ, а не вторым.** У этой ветви нет
   `firestore.get()`, и при коротком замыкании `||` чтение своей записи не
   стоит обращения к Firestore вовсе — а заодно переживает случай, когда
   документа вечера уже нет (тогда ветвь владельца даёт `Null value error`,
   тот самый класс, что чинили 14.09). **Короткое замыкание здесь — свойство
   языка правил, а не наш замер (I50);** проверяется оно так же, как 14.09:
   счётом `Null value error` в логе прогона;
3. **проверка «а в составе ли ты» у читателя не остаётся** — и это
   безопасно, потому что **положить** файл под своим uid может только тот,
   кто в составе (правило записи не тронуто). Файла, которого не клал
   участник, там не бывает; чтение несуществующего даёт 404, а не утечку.

**Правило записи не трогается ни в одном знаке.**

## 6.3. Что зовёт это чтение в клиенте и от чьего имени

**Мест, трогающих путь, в `lib` два** (`grep -rn "event_leave_notes\|leaveNoteVoicePath\|uploadLeaveNoteVoice" lib`):
`leaveNoteVoicePath` (`leave_note.dart:149`, только строит адрес) и
`uploadLeaveNoteVoice` (`firestore_service.dart:2173`). **В `functions/src`
— ноль:** сервер к этой папке не ходит вовсе.

**Чтений по правилам ровно одно, и оно от имени вышедшего:**

- `uploadLeaveNoteVoice` → `_uploadVoiceFile` → **`getDownloadURL()`**
  (`firestore_service.dart:2138`). Зовётся сразу после загрузки, **самим
  загрузившим**. `getDownloadURL()` — операция чтения, то есть правило
  чтения к ней применяется. **После сужения он проходит по новой ветви
  `request.auth.uid == uid`** — ради этого ветвь и нужна; убери её, и
  сломается сама отправка причины.

**А ПОКАЗ ИДЁТ МИМО ПРАВИЛ — и это главное, что надо знать перед выкладкой.**
`VoicePlayer` получает `audioURL` = готовый `voiceUrl` из документа и зовёт
`_player.setUrl(...)` (`voice_player.dart:198`) — это обычный HTTPS-запрос по
ссылке с токеном. Замер 15.09 доказал, что такой запрос **не спрашивает
правил вовсе**: анонимный `curl` — 200, тот же путь без `token=` — 403.

**Отсюда два следствия, оба неприятные и оба обязаны быть сказанными:**

1. **Сужение сегодня НЕ МОЖЕТ сломать показ.** Владелец слушает по токену, а
   не по праву. Живого пути, который читает файл не владельцем и не
   вышедшим, в клиенте **нет ни одного**;
2. **И по той же причине выкладку НЕЛЬЗЯ проверить на трубке.** Проба
   «нажал „?“, голос звучит» будет зелёной и при верном правиле, и при
   вывернутом наизнанку — показ до правила не доходит. Это I14 в чистом
   виде: **назвать, каким был бы вывод при поломке — он совпадает с выводом
   на исправном, значит проба не говорит ничего.**

**Чем тогда проверяется выкладка — тремя вещами, и трубки среди них нет:**

- прогон правил на эмуляторе (6.4);
- сверка выложенного источника с файлом: сегодня прод **байт в байт равен**
  `storage.rules` — `diff` даёт **0 расхождений** при **канарейке 53**
  (тот же `diff` против прежней редакции `96e5bbb`), замер 15.09;
