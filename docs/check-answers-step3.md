# Прогон шага 3 — «договоры и мероприятия одна сущность»

> ## ПРОВЕРЯЕТСЯ, ЧТО НИЧЕГО НЕ СЛОМАЛОСЬ. НОВОЕ ПОВЕДЕНИЕ НЕ ПРОВЕРЯЕТСЯ — ЕГО НЕТ
>
> **Шаг 3 нового поведения не даёт вовсе.** Показ состава тот же, напоминания
> те же, ни одна кнопка не появилась и не исчезла. Модель научилась отдавать
> ответ участника, сервер — фильтровать напоминания по нему, и оба читают поле,
> у которого **сегодня одно значение на всех** (`going`): писателя `waiting` и
> `cant` нет до шага 4.
>
> **Зелёный прогон здесь означает ровно одно: старое не испорчено.** Он НЕ
> означает, что новое работает — новому пока нечего показывать. Прочитать его
> шире — значит записать себе проверку, которой не было (I40 про знаменатель:
> «прошло 5 из 5» без этой рамки читается как «фича работает»).
>
> **Зачем тогда прогон.** Чтение нового поля идёт по записям, где поля **нет**,
> а таких на 10.08 — **75 из 75**. Жёсткое приведение типа на таком чтении уже
> один раз уронило бы карточку целиком (поймано тестом, I49). Прогон отвечает
> на один вопрос: **не падает ли старое от нового чтения.**

**Сборка:** собрана 11.08 начисто после того, как `codesign --verify --deep
--strict` отказал на инкрементальной — **N89 воспроизвелась второй раз**
(первый 09.08). Подпись и содержимое проверены отдельными командами, поиск
строк по UTF-16 (N103).

## Пункт 1. Рафаэль: список договоров открывается

Открыть вкладку **«Müqavilələr»**.

**Должно быть:** список открылся, карточки на месте, ни одна не пустая и ни
одной ошибки на экране. Числа во вкладках такие же, как были.

**Чего быть НЕ должно:** пустого списка, серого экрана, надписи об ошибке.

## Пункт 2. Рафаэль: карточка договора и состав

Открыть любой договор.

**Должно быть:** состав виден, имена целы (не uid), фишки участников
кликаются.

**Почему именно состав:** модель теперь разбирает поле `answers` рядом с
`musicians`. Если разбор споткнётся, первым пропадёт или сломается именно
состав.

## Пункт 5. Журналом с Mac: напоминания не падают

Проверяю я, не с трубки. Функция напоминаний теперь читает `answers` и на
записях без поля обязана идти запасным путём.

```
gcloud logging read 'resource.labels.service_name="sendeventreminders"' \
  --project=mugam-club --limit=20 --freshness=2h \
  --format="value(timestamp,textPayload)"
```

**Должно быть:** ни одного исключения. Отсутствие строк само по себе ничего не
доказывает — напоминания идут по расписанию, и если окно не наступало, писать
было нечего (**I14**: пустой вывод не хорошая новость). Поэтому вердикт
здесь — «падений нет **при N прогонах за окно**», а не «падений нет».

## Чего этот прогон не проверяет — названо, чтобы не дочитали лишнего

- **ответ участника «ждём» и «не может»** — писателя нет до шага 4;
- **фильтр напоминаний в деле** — все ответы `going`, никто не отфильтрован;
- **показ ответов в составе** — экрана шаг 3 не трогает намеренно: ярлык,
  одинаковый у всех, это N109, и мы завели бы её сами (`docs/plan.md`, шаг 3);
- **расхождения записи с составом** — их считает перепись
  `functions/src/scripts/censusAnswers.ts`, а не глаз: база 10.08 — 0
  расхождений при 75 документах.
