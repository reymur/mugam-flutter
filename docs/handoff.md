#### 3. Работа №6 — отмена договора по согласию

**Порядок изменён по находке 04.08: серверная часть ПЕРВОЙ.** Отзыв
запроса отмены сейчас на сервере не выражен вовсе — правила на снятие
`cancelRequestedBy`/`cancelRequestedAt` нет, клиент получит отказ.

Строить **однопутно** — только карточка договора. Гарантия «по согласию»
и так на сервере (`requestsCancel`/`confirmsCancel` написаны), а каждая
лишняя дорога — ещё одно место, где забудут.

**Разбор сделан, писать по нему:**

- **Отзыв и отказ — два разных поступка с одинаковым следом в данных.**
  Отзыв — запросивший передумал, извещать вторую сторону. Отказ — вторая
  сторона не согласна, извещать запросившего. Триггер видит `before`/
  `after`, но не видит, кто писал, поэтому поступок обязан называться в
  самой записи: `lastActionType` ∈ `cancelWithdrawn` / `cancelDeclined`,
  плюс `stampsSelf()`, и название связано с тем, кто его совершает —
  тогда подделать нельзя.
- **После подтверждения отзыв невозможен:** `status != 'cancelled'`, и
  `status` этим ходом не трогать вовсе.
- **Одновременность решают правила, не UI.** Кто первый записал, тот и
  прав: после отзыва подтверждение отклонится (`cancelRequestedBy` стал
  `null`), после подтверждения отзыв отклонится (`status == 'cancelled'`).
  **Отказ проигравшему НЕЛЬЗЯ глотать** — он обязан стать словами «вторая
  сторона уже подтвердила отмену».
- **Признак нового запроса — по `cancelRequestedAt`, а не по появлению
  поля** (класс N29 дословно).
- **Заодно закрыть N36** тем же условием `status != 'cancelled'` в
  `confirmsCancel()`.

```
}
function withdrawsCancelRequest() {   // запросивший передумал
  return clearsCancelFields()
    && resource.data.get('cancelRequestedBy', null) == request.auth.uid
    && request.resource.data.lastActionType == 'cancelWithdrawn';
}
function declinesCancelRequest() {    // вторая сторона не согласна
  return clearsCancelFields()
    && resource.data.get('cancelRequestedBy', null) != request.auth.uid
    && request.resource.data.lastActionType == 'cancelDeclined';
}
```

**Порядок работ: правила → парный тест → UI.** Тест обязан покрыть обе
дороги отдельно (разрешено кому положено, отказ всем прочим) и щель N36 —
повторное подтверждение после `cancelled` должно отклоняться.

#### ПЕРВОЕ. Тест форм запросов в эмуляторе

**Зачем именно сейчас, а не «когда-нибудь».** За сессию 03–04.08
`permission-denied` укусил **дважды**, оба раза по одной причине: запрос
фильтровал не по тому, чем правило чтения доказывается. Правило Firestore
разрешает выборку, только если **сами фильтры запроса** доказывают право
на КАЖДЫЙ возможный результат — сервер не читает документы, чтобы это
выяснить. Оба раза дефект вылезал на трубке, в проде, молча (кнопка
залипала). Работа №6 добавляет и новые запросы, и новые правила — тест,
сделанный ДО неё, ловит её ошибки сам.

**Что именно строить.** Файл `functions/test/query-shapes.test.ts`. На
каждый `.where(`-запрос, который клиент реально выпускает, — один случай:
поднять его форму один в один против настоящего `firestore.rules` в
эмуляторе и потребовать `assertSucceeds`. Плюс к каждому — парный
`assertFails` на форму БЕЗ доказывающего фильтра, иначе тест не отличает
разрешение от «правила вообще не проверялись».

**Откуда брать список форм:**
```
grep -rn "\.where(" lib/ --include=*.dart
```
Основной источник — `lib/firebase/firestore_service.dart`; проверить и
остальные файлы из вывода, запросы живут не только там.

**Как это запускается** (эмулятор поднимается сам, отдельная команда не
нужна, проект `demo-mugam-test` подставляется скриптом):
```
cd functions && npm test
```
Один файл:
```
cd functions && npx jest test/query-shapes.test.ts --runInBand
```

**Образец для копирования** — `functions/test/rules.test.ts`: там уже
готовы `initializeTestEnvironment` с чтением настоящего `firestore.rules`
с диска, `assertSucceeds`/`assertFails` и посев данных через
`withSecurityRulesDisabled`. Общие константы — `functions/test/helpers.ts`.

**Обязательная проверка возвратом** (правило №2 ниже): выкинуть из одной
формы доказывающий фильтр — например `where('musicians', arrayContains:
uid)` — и убедиться, что тест **падает**. Не упал — тест бесполезен,
именно так уже был пропущен дефект в прод.

**Потом, отдельным шагом:** проход по `.where(`-цепочкам в CI, чтобы
новый запрос нельзя было добавить мимо теста. Это средство сильнее
комментария, а комментарий на этом самом месте уже один раз не сработал

#### ВТОРОЕ. Работа №6 — отмена договора по согласию

Последнее, что осталось в Этапе I. Она же оживит два уже написанных

3. **Признак не строить так, будто прошлого не было.** Проверяется

### Препятствие оказалось не тем, чем записано — поправка 03.08

Прежняя редакция утверждала: «кабель Рафаэля не даёт данные,
`system_profiler SPUSBDataType` не видит ни одного iPhone на шине вовсе».
**Первая половина неверна, вторая получена негодной командой.**

`system_profiler SPUSBDataType` на этой машине (macOS 26.4) возвращает
**ноль строк всегда**, есть на шине устройства или нет: тип данных
переименован в `SPUSBHostDataType`. Из пустого вывода был сделан вывод о
пустой шине — ложный отрицательный, уведший диагностику на кабель.

Рабочие проверки:

```
system_profiler SPUSBHostDataType | grep -A8 iPhone     # даёт Serial Number
ioreg -rc IOUSBHostDevice -w0 | grep '"USB Product Name"'
xcrun devicectl device info details --device <id> | grep -iE "tunnelState|lastConnectionDate"
```

Серийник в `SPUSBHostDataType` идёт **без дефиса**
(`00008101001A146911A3003A`), в `flutter devices` — с дефисом после
восьмого символа. Сверять надо именно серийник: 03.08 на кабеле висел не
Рафаэль, а Teymur, и конспект приписывал кабель не тому телефону.

**Настоящей причиной был кабель, но диагностируется она иначе.** Признак
исправного подключения — `tunnelState: connected` и **сдвигающийся**
`lastConnectionDate`. Пока Рафаэль был недоступен, `lastConnectionDate`
стоял намертво на времени первого появления: устройство мелькнуло на шине
и больше не соединялось. Перезапуск `remotepairingd` и `CoreDeviceService`
(оба под пользователем, `kill` без sudo, launchd поднимает обратно) не
помог и помочь не мог — туннель было не к чему поднимать, к моменту
проверки телефона на шине не было вовсе. Помогло переподключение кабеля:
серийник появился, `tunnelState` стал `connected`, `lastConnectionDate`
сдвинулся, `flutter devices` увидел устройство.

> Прежде чем винить кабель, порт или доверие к компьютеру — посмотреть,
> есть ли телефон на шине **годной командой**, и сверить серийник с тем,
> который ожидается.

### Ещё одно, чего в прежней редакции не было

`flutter run` **сама поднимает Xcode.app** на фазе установки («You may be
prompted to give access to control Xcode»). То есть требование «Xcode
закрыт» относится к состоянию ДО запуска; после первой же сборки он
окажется открыт, и перед следующей его надо закрывать заново
(`osascript -e 'quit app "Xcode"'`).

Перестановка кабеля **на фазе установки** её срывает: у Teymur
компиляция прошла, а присоединиться не удалось («The mDNS query for an
attached iOS device failed»), и сборку пришлось повторять целиком. Строки
`Flutter run key commands.` в логе при этом не было — то есть установка
осталась недоказанной, и повтор был обязателен, а не перестраховкой.

### Как собирать

```
pgrep -f "Xcode.app/Contents/MacOS/Xcode"      # ДОЛЖНО быть пусто
stdbuf -oL -eL flutter run --release -d <device-id> > build_X.log 2>&1
```

#### `--release` обязателен, и вот чего стоило его отсутствие

**Прежняя редакция этого блока давала команду без флага**, то есть
отладочную сборку, — при том что все состоявшиеся прогоны на устройствах
записаны в реестре как релизные («боевая сборка, релиз» — `AUDIT_TODO.md`
строки 339, 776, 1815). Инструкция расходилась с тем, чем на самом деле
пользовались, и расхождение было невидимым: обе сборки одинаково дают
`Flutter run key commands.`, то есть **доказательство установки у них не
различается**.

Цена расхождения, заплаченная 03.08 вечером: отладочные сборки поставлены
на обе трубки, после чего проверки оказались невозможны, и обе трубки
пришлось пересобирать заново.

**Три свойства отладочной сборки, измеренные в тот вечер:**

1. **Она не запускается с иконки.** Тап по иконке даёт чёрный экран —
   наблюдалось на обеих трубках независимо. Ей нужна живая сессия.
2. **Сессия рвётся от закрытия Xcode.** У Teymur при живой сессии
   закрытие Xcode дало `Lost connection to device.` в логе, приложение
   умерло. Механизм виден в списке процессов: отладочный запуск идёт
   **через Xcode** — `flutter` держит помощника
   `xcode_debug.js --xcode-path /Applications/Xcode.app … --device-id …`.
3. **Вторую сборку не запустить, не закрыв Xcode** (см. правило ниже), а
   закрытие убивает первую трубку.

Вместе это значит: **на отладочных сборках две трубки не могут быть живы
одновременно.** А проверки «вдвоём» — пункт 3 и подсветка — требуют ровно
двух живых телефонов. Релизная сборка ни одного из трёх свойств не имеет:
AOT-приложение живёт с иконки само, отцепление и закрытие Xcode ему
безразличны.

> Собирать **только релиз**. Отладочная сборка выглядит установленной так
> же, как релизная, и расходится с ней лишь тогда, когда телефон
> понадобится вторым.

- **Xcode.app обязан быть закрыт.** При открытом Xcode запуск на Teymur
  сорвался 03.08 с `Error starting debug session in Xcode: Timed out
  waiting for CONFIGURATION_BUILD_DIR to update` — приложение не встало
  вовсе. После закрытия та же сборка прошла. Воспроизведено вечером того
  же дня на Рафаэле: правило держится, обойти его «дешёвой пробой» не
  вышло.
- **Убитая сборка оставляет сироту, который поднимает Xcode обратно.**
  После `pkill` по `flutter run` процесс
  `osascript … xcode_debug.js` остаётся жить и переоткрывает Xcode, из-за
  чего `quit app "Xcode"` выглядит не сработавшим. Снимать помощника
  первым:
  `pkill -f "xcode_debug.js"`, только потом Xcode.
- `flutter run` **сам не завершается**. Ждать его выхода бессмысленно:
  признак готовности — строка `Flutter run key commands.` в логе.
  **Отцепляться только когда телефоны больше не нужны**, а не сразу по
  появлении строки: у релизной сборки приложение переживает отцепление, у
  отладочной — нет (проверено 03.08 на обеих трубках).
- Вывод собирать **построчно в файл**, не через `| tail`: иначе лога не
  будет вовсе до конца процесса.
- `Running Xcode build...` идёт **без перевода строки** — лог не растёт,
  и это нормально. Живость сборки проверять по процессам `xcodebuild` и
  `clang`, а не по логу.
- Времена: при полной пересборке нативной части Рафаэль по кабелю 1096 с
  + 353 с; при живом кеше — 90,4 с + 130,3 с (кабель) и 57,2 с + ~4 мин

   сторона соглашается — и он в двух местах разом, а выясняется это в день
   события. Выпускать главную фичу с дырой в центре нельзя.

   календаре. Разойдись список пунктов хоть на символ — выбранное молча

4. **Участники не переносятся** — в чате один на один стороны заданы

**Правило, записанное в шапке файла:** расхождение листа с календарным
окном либо перечислено там с причиной, либо считается ошибкой. Прежний
комментарий был неполон, и из-за слова «намеренно» потерянные отличия
выглядели решением.

### `e4fd183` — что именно и почему

Замечание владельца прямо с прогона: **в календаре человек видит дату
целиком и понимает, занята она или нет, а в листе видит только колесо** —
и о том, что на этот день у него уже что-то есть, не узнаёт, пока не
совпадёт минута в минуту. А совпадения минут в жизни почти не бывает:
мешает не одинаковое время, а второй тədbir в тот же день.

Предупреждение и диалог теперь поднимаются на **четырёх** случаях, и
порядок между ними не произволен — запреты старше находок, точное
совпадение старше занятого дня (оно говорит больше):

1. запрет на минуту («я сам попросил другое время»);
2. запрет на день («я сам попросил другой день»);
3. точное совпадение времени;
4. занятый день.

**Запрет от «Yeni tədbir» ставится ровно на то, о чём спрашивали:**
совпала минута — занята минута, занят день — занят день, и снимается
каждый своим действием (сдвигом времени / сменой дня). Иначе ответ
«выберу другое» снимался бы действием, которого человек не делал.

Диалог — тот же календарный, второго не заводили.

Само предупреждение переделано по просьбе владельца («читабельнее и
красивее»): две строки вместо одной (заголовок «что не так», подпись «чем
именно занято»), значок вынесен в свой кружок слева — эмодзи внутри строки
уезжал вместе с переносом и терял смысл отметки на полях. При нескольких
мероприятиях в день перечисляются все, по возрастанию времени.

**Идея владельца, записанная в план** (`docs/job-offer-plan.md`, раздел
«Импорт мероприятий из фото»): музыкант присылает фото своего списка
(скриншот календаря телефона, страница ежедневника), приложение
распознаёт даты и названия, показывает разобранное на подтверждение,
человек правит и создаёт мероприятия. **Фича переходного периода** —
нужна один-два раза при переезде в приложение, поэтому стоимость
распознавания мизерная, а приоритет ниже договоров. Корень проблемы
(детали теряются в голосовых) закрывают сами договоры; импорт решает
только перенос накопленного. Четыре вопроса записаны открытыми.

## 5б. Класс «утверждение об инструменте, не проверенное на инструменте»

Назван вечером 03.08, когда третья поправка подряд оказалась той же
формы. Записан отдельно, потому что это не три случайности, а один
повторяющийся способ ошибаться — и он дороже ошибок в коде.

**Форма.** Утверждение говорит не о поведении приложения, а о том, **чем
и как за приложением можно наблюдать**. Оно попадает в конспект без
проверки самого инструмента — и дальше молча определяет, каким способом
вообще ищут ответы.

| # | Утверждение | Чем оказалось | Что оно стоило |
|---|---|---|---|
| 1 | «`system_profiler SPUSBDataType` не видит ни одного iPhone на шине» | команда возвращает ноль строк **всегда** на этой macOS: тип переименован в `SPUSBHostDataType`. Ложный отрицательный | диагностику увело на кабель, чинили не то |
| 2 | «`debugPrint` не виден, поэтому единственный способ — вывод на экран» | посылка верна для **релиза**, вывод неверен вообще: при отладочной сборке с прицепленной сессией логи и стеки видны | несколько прогонов диагностировали вслепую при доступных логах |
| 3 | «строка `Flutter run key commands.` доказывает готовность трубки» | доказывает только «сборка встала». Релиз и debug дают её **одинаково**, а разница между ними решает, возможна ли проверка вообще | вечер 03.08: обе трубки числились готовыми и готовыми не были, пересборка целиком |

**Общее у всех трёх:** проверялся результат инструмента, а не сам
инструмент. Пустой вывод команды приняли за пустую шину; отсутствие
логов — за свойство устройств; появление строки — за готовность к
проверке. Во всех трёх случаях ошибка **не выглядит ошибкой**: инструмент
молчит ровно так же, как когда всё в порядке.

**Признак для поиска следующего:** утверждение вида «здесь нельзя
посмотреть X» или «X доказывается тем-то». Спрашивать не «верно ли это»,
а два других вопроса:

1. **чем проверено, что инструмент вообще работает** — что он показывает,
   когда искомое заведомо есть;
2. **чего этот признак не различает** — какие два разных состояния дают
   один и тот же вывод.

Второй вопрос и вскрыл случай 3: строка-доказательство честно отличает
«встало» от «не встало» и не отличает **ничего больше**.

**Кандидаты, оставшиеся непроверенными** (не находки, а места, где
утверждение об условиях наблюдения сделано рассуждением и на нём стоит
решение НЕ проверять):

- `AUDIT_TODO.md:1884` — «ступень „⏳ çoxdan görünmür“ на устройствах
  недостижима (нужны сутки без заходов)». Выведено из порога, не
  замерено. Достижима как минимум двумя путями — сутки не трогать трубку
  либо третий аккаунт, — то есть «недостижима» сильнее, чем есть.
- `AUDIT_TODO.md:130` — «состояние „Söhbət yüklənmədi“ из списка чатов
  недостижимо». Опирается на рассуждение о том, что офлайн-кэш всегда
  отдаёт документ чата; искусственная проверка ставилась на другую
  половину утверждения (достижимость через пуш).

Оба помечены здесь, а не переписаны: они могут быть верны. Отмечено
именно то, что **проверены они не были**, а решение не проверять принято
на них.

## 6. Правила, выведенные за эту сессию

- **Отчёт механизма и проверка механизма должны быть разными обходами.**
  Сборщик сирот сам себе сказал «удалил двоих законно»; поверить этому
  можно было только отдельным проходом по всей базе, ищущим ссылки на
  удалённое. Иначе проверяется самосогласованность, а не факт.
- **Комментарий у числа держит запрет крепче, чем реестр.** У
  `DEFAULT_MIN_AGE_MS` прежний текст сам приглашал сузить окно
  («реальный разрыв — секунды»), и правило снялось бы при первом чтении
  кода. Причина должна лежать рядом с числом.
- **Локальная запись возвращается в поток раньше, чем закроется форма.**
  Firestore отдаёт её из кеша немедленно. Всё, что различает «своё» и
  «чужое», должно объявляться ДО записи, а не после.
- **Ключ по подписи на экране ломается на втором экране.** Подписи строк
  у двух карточек разные; ключевать надо по имени поля.
- **Проверка «на глаз» не отличает старую сборку от новой.** Список
  процессов на телефоне одинаков. Доказательство — либо поведение,
  которого старая сборка не умеет, либо строка `Flutter run key commands`
  в логе.
  > **Поправка 03.08, вечер: эта строка доказывает меньше, чем ей
  > приписывали.** Она означает «сборка встала», и только. Она **не**
  > отличает релиз от debug — обе дают её одинаково, — а от этого
  > различия зависит, можно ли вообще провести проверку (см. блок «Как
  > собирать»). Весь вечер обе трубки числились готовыми по этой строке
  > и готовыми не были. Признак, который называют доказательством,
  > обязан быть проверен и на то, чего он **не** различает.
- **Утверждение об условиях наблюдения дороже утверждения о поле.**
  Первое определяет не ответ, а способ его искать, и ошибается молча:
  отсутствие логов выглядит свойством устройств, а не следствием флага
  сборки. Разбор — в реестре, врезка к «Условиям наблюдения» (A5).
  Отсюда правило: **запись вида «здесь нельзя посмотреть X» проверять
  так же, как замер** — называть, при каких условиях она получена, и
  чем именно проверялась.
