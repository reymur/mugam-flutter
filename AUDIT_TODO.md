`system_profiler` не видит по USB ни одного устройства, по сети телефон тоже
не отвечает, при том что второй виден и работает): двусторонняя переписка на

sil» на последнем входящем. Это единственное непроверенное по Этапу 4.

Состояние «Söhbət yüklənmədi» **из списка чатов недостижимо, через пуш —
достижимо**. `watchChats` запрашивает саму коллекцию `chats`, то есть те же
документы, на которых лежит отсечка, а офлайн-кэш Firestore включён (по
умолчанию, настройки не переопределены) — поэтому чат, открытый из списка,
всегда получает отсечку из кэша, даже без сети. Но список не единственный
вход: `main.dart:198-203` на тап по пушу делает `appRouter.push('/chat/…')`,
включая холодный старт из убитого приложения (`getInitialMessage`), а
`chatsProvider` подписан только на вкладке «Mesajlar», а не глобально.
Условие срабатывания: документа чата нет в кэше **и** сети нет или она
медленная в момент открытия по пушу.

Пуши в приложении реализованы, но **выключены** (нет платного аккаунта
Apple, см. заметку об аккаунте), поэтому естественным путём ветка сегодня не
срабатывает и на устройстве в реальном сценарии непроверяема.

**Проверено искусственно 02.08.** На одну сборку `watchChatClearedAt` был
подменён на поток, который никогда ничего не отдаёт; сборка ставилась
начисто, чтобы стереть локальную запись об отсечке, при живой серверной
(чат перед этим чистился). Результат на устройстве: спиннер при входе →
через ~4 с «Söhbət yüklənmədi / Bağlantınızı yoxlayın» → кнопка «Yenidən
cəhd et» каждый раз возвращает спиннер и затем ошибку. Главное:
**доочисточные сообщения не появились ни в одном кадре**, хотя сеть была и
сообщения в локальное хранилище приезжали. Подмена снята, в репозиторий не
попала. Надписи после прогона увеличены — на устройстве были нечитаемы.

🔁 **Перепроверить в день включения пушей**: ветка заработает сразу у всех,
и естественный сценарий (пуш пришёл на связи, тапнули уже без неё) станет
достижимым.

### Класс «пустой снимок принят за содержательный ответ» — обход 02.08

Три находки подряд оказались одним классом (`null` в `_clearedAt` → «поля
нет» → «документа нет»), поэтому по нему прошлись отдельно. Признак, по
которому классифицировали: **переживает ли неверный ответ приход верных
данных.**

| Место | Что принимается за ответ | Переживает связь |
|---|---|---|
| `watchChatClearedAt` → `setClearedAt` | «документа нет» → «никогда не чистили» | **да** — писалось на диск (N13, закрыт) |
| `watchChats` → список чатов | пустой запрос из кэша → «Hələ mesaj yoxdur» | нет (N14, открыт) |
| `watchChatMedia`, избранные, договоры | пустой запрос → «ничего нет» | нет |
| `watchChatMeta` (`?? {}` у `deliveredTo`/`lastReadMsgId`/`lastReadAt`/`unreadCount`/`members`) | документа нет → пустые карты | нет; направление безопасное — пропавший `unreadCount` даёт 0 и не запускает починку |
| `watchChatTyping` (`?? {}`) | документа нет → никто не печатает | нет |
| `markChatAsReadBy`, `refreshChatPreviewIfStale` | неполный локальный список → «самое новое» | нет, сходится по мере прихода данных (незатухающую половину закрыл N11) |
| `LocalMessageStore.upsertManyFromFirestore` (свойство закреплено комментарием) | — | **корректно по построению**: пустой снимок ничего не пишет и ничего не удаляет, поэтому «пусто из кэша» не может быть принято за «всё исчезло». Единственное место, где эта ошибка была бы катастрофической |

Вывод: durable-разновидность в проекте была ровно одна и закрыта. Остальное
— transient, лечится сетью; из них только N14 успевает соврать пользователю
словами.

### Диагностика сирот 02.08 — корень найден

**Файл всегда заливается раньше документа.** `uploadStatusVideo/Image` →
`createStatus`; `uploadChatImage/Video/File` → документ сообщения;
`uploadAvatar` → `updateUserProfile`; `uploadGroupPhoto` → `updateGroupInfo`.
Порядок одинаков везде — это не отдельная ошибка, а устройство всех путей
загрузки: Storage и Firestore не делят транзакцию.

**Чистилка привязана к удалению документа.** `onStatusDeleted` срабатывает
на удаление `users/{uid}/statuses/{id}`. Объект, у которого документа
никогда не было, для неё недостижим **навсегда**, сколько бы она ни
работала. Логи это подтверждают: в окне 16.07 09:22–10:08 и 23.07 20:43,
когда заливались сироты, вызовов функции нет вовсе — документы не удалялись,
их не существовало.

Сироты — нарезка длинного видео (`..._30000.mp4`, `_60000`, `_90000`,
`_150000` — 30-секундные куски) плюс серия фото. Цикл публикации сегментов
намеренно неатомарен, и при сбое на `createStatus` уже залитый кусок
остаётся ничьим. 35 сирот = 35 разных `statusId`.

**Взгляд вбок (по требованию) — где ещё тот же порядок:**

| Путь | Имя объекта | Накопление |
|---|---|---|
| статусы | уникальное на загрузку | **не ограничено** — 35 шт / 110 МБ |
| медиа чата | уникальное на загрузку | **не ограничено** — 3 шт / 2.5 МБ, свежие |
| аватар | фиксированное `avatars/{uid}.jpg` | ограничено 1 на пользователя, перезаписывается |
| фото группы | фиксированное `groups/{chatId}/avatar.jpg` | ограничено 1 на группу, перезаписывается |

То есть порядок «файл раньше документа» универсален, но течёт только там,
где имя уникально на каждую загрузку. Аватары и фото групп самоограничены по
построению — чинить нечего.

**Следствие для плана:** B11 (медиа чатов), backlog статусов и половина
B19/B21 (частично залитое не удаляется при отмене) — **одна и та же
проблема**. Отменённая загрузка оставляет объект, на который не ссылается ни
один документ, то есть ровно ту же сироту. Значит и механизм нужен один:
сборщик, который удаляет объекты старше окна ожидания, на которые не
ссылается ни один документ. По принципу переносов он идемпотентен по природе
(проверка существования, потом удаление), поэтому повторный запуск и
параллельная живая загрузка ему безопасны.

### Сборщик сирот и чистка 02.08 — сделано

Механизм один на все три находки (`097994f`, `a96d3e3`, `eafcd67`,
`5ce4523`): `functions/src/orphanSweep.ts` + регулярная
`sweepOrphanMediaDaily` + разовый скрипт. Сирота — объект, на который не
ссылается ни один документ **во всей базе** и который старше суток.

Два места, где рассуждение чуть не стоило живого медиа, оба найдены
проверкой, а не чтением кода, и оба закреплены комментарием в шапке
сборщика:

1. **Пересылка переиспользует URL** (`forwardMessage`): сообщение в чате
   B штатно ссылается на объект под `chats/A/`. Сборщик «по своему чату»
   удалил бы медиа у всех, кому переслали, и в чате-владельце это
   выглядело бы корректно. Множество ссылок — глобальное.
2. **Список коллекций устаревает молча.** Первая версия смотрела
   messages/statuses/chats/users — 319 документов из 805 реальных;

третье правило: при пустом ИЛИ прерванном обходе не удаляется ничего.

### N3 закрыт не переносом, а упразднением счётчика

Задача звучала как «перенести `mediaImageCount` на сервер», и обе её
половины упирались в одно: инкремент не идемпотентен, поэтому пока живы
старые сборки, любой перенос даёт двойной учёт или недосчёт, а
флаг-маркер версии в схеме признан хуже самой проблемы.

Разрешилось тем, что считать оказалось нечего. Число читал ровно один
потребитель — трейлинг у плитки «Media, keçidlər və sənədlər», причём
нажатие на неё до сих пор заглушка. Ради этого числа на КАЖДУЮ
отправленную фотографию уходила отдельная запись в `chats/{chatId}` — в
тот самый документ, ради которого превью свели в одну транзакцию (B16), а
слушателей — в одного (B17).

Теперь число берётся двумя агрегатными запросами на том экране, который
его показывает: `count(type == image)` минус `count(type == image &&
deletedForAll == true)`. Вычитание — потому что «не удалено у всех» в
Firestore не выражается: у большинства сообщений поля нет вовсе, а запрос
по отсутствующему полю не находит ничего. Итог: точное число за одно-два
чтения, минус запись на каждую фотографию, и ни поля, которое может
разъехаться, ни миграционного окна, ни пересчёта.

Соседняя плитка «Seçilmişlər» в том же файле считала так с самого начала.

`test/local_message_store_trim_test.dart` — 8 тестов на **боевой** константе

в чужой чат не трогает открытый» (тот самый сценарий, из-за которого
граница не привязана к порядку доступа), выживание неотправленных с
`seq == null`, отсутствие дублей и порядок по seq, догрузка старой страницы

прокрутки, квитанции), проверялись на устройстве **на временно понижённом

репозиторий не попала, боевое значение пересобрано и проверено.

Формулировка, уточнённая упавшим тестом: **чат вне экрана может быть урезан
при открытии любого другого — это задумано**; проверять надо, что открытие
чата не урезает его самого.

**Принцип для всех переносов клиент→сервер** (выведен при откате
`mediaImageCount`): переносить только операции, **идемпотентные по своей
природе** — пересчёт вместо инкремента, проверка существования перед
удалением вместо слепого delete. Тогда старая сборка, делающая то же
самое, не ломает результат, а безвредно дублирует. Флаги-маркеры версии в
схеме ради миграционного окна — хуже самой проблемы.
