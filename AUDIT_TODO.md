достижимо**. `watchChats` запрашивает саму коллекцию `chats`, то есть те же
документы, на которых лежит отсечка, а офлайн-кэш Firestore включён (по
умолчанию, настройки не переопределены) — поэтому чат, открытый из списка,
всегда получает отсечку из кэша, даже без сети. Но список не единственный
вход: `main.dart:198-203` на тап по пушу делает `appRouter.push('/chat/…')`,
включая холодный старт из убитого приложения (`getInitialMessage`), а
`chatsProvider` подписан только на вкладке «Mesajlar», а не глобально.
Условие срабатывания: документа чата нет в кэше **и** сети нет или она
медленная в момент открытия по пушу.

Пуши в приложении реализованы, но **выключены** (нет платного аккаунта
Apple, см. заметку об аккаунте), поэтому естественным путём ветка сегодня не
срабатывает и на устройстве в реальном сценарии непроверяема.

**Проверено искусственно 02.08.** На одну сборку `watchChatClearedAt` был
подменён на поток, который никогда ничего не отдаёт; сборка ставилась
начисто, чтобы стереть локальную запись об отсечке, при живой серверной
(чат перед этим чистился). Результат на устройстве: спиннер при входе →
через ~4 с «Söhbət yüklənmədi / Bağlantınızı yoxlayın» → кнопка «Yenidən
cəhd et» каждый раз возвращает спиннер и затем ошибку. Главное:
**доочисточные сообщения не появились ни в одном кадре**, хотя сеть была и
сообщения в локальное хранилище приезжали. Подмена снята, в репозиторий не
попала. Надписи после прогона увеличены — на устройстве были нечитаемы.

🔁 **Перепроверить в день включения пушей**: ветка заработает сразу у всех,
и естественный сценарий (пуш пришёл на связи, тапнули уже без неё) станет
достижимым.

### Класс «пустой снимок принят за содержательный ответ» — обход 02.08

Три находки подряд оказались одним классом (`null` в `_clearedAt` → «поля
нет» → «документа нет»), поэтому по нему прошлись отдельно. Признак, по
которому классифицировали: **переживает ли неверный ответ приход верных
данных.**

| Место | Что принимается за ответ | Переживает связь |
|---|---|---|
| `watchChatClearedAt` → `setClearedAt` | «документа нет» → «никогда не чистили» | **да** — писалось на диск (N13, закрыт) |
| `watchChats` → список чатов | пустой запрос из кэша → «Hələ mesaj yoxdur» | нет (N14, открыт) |
| `watchChatMedia`, избранные, договоры | пустой запрос → «ничего нет» | нет |
| `watchChatMeta` (`?? {}` у `deliveredTo`/`lastReadMsgId`/`lastReadAt`/`unreadCount`/`members`) | документа нет → пустые карты | нет; направление безопасное — пропавший `unreadCount` даёт 0 и не запускает починку |
| `watchChatTyping` (`?? {}`) | документа нет → никто не печатает | нет |
| `markChatAsReadBy`, `refreshChatPreviewIfStale` | неполный локальный список → «самое новое» | нет, сходится по мере прихода данных (незатухающую половину закрыл N11) |
| `LocalMessageStore.upsertManyFromFirestore` (свойство закреплено комментарием) | — | **корректно по построению**: пустой снимок ничего не пишет и ничего не удаляет, поэтому «пусто из кэша» не может быть принято за «всё исчезло». Единственное место, где эта ошибка была бы катастрофической |

Вывод: durable-разновидность в проекте была ровно одна и закрыта. Остальное
— transient, лечится сетью; из них только N14 успевает соврать пользователю
словами.

### Диагностика сирот 02.08 — корень найден

**Файл всегда заливается раньше документа.** `uploadStatusVideo/Image` →
`createStatus`; `uploadChatImage/Video/File` → документ сообщения;
`uploadAvatar` → `updateUserProfile`; `uploadGroupPhoto` → `updateGroupInfo`.
Порядок одинаков везде — это не отдельная ошибка, а устройство всех путей
загрузки: Storage и Firestore не делят транзакцию.

**Чистилка привязана к удалению документа.** `onStatusDeleted` срабатывает
на удаление `users/{uid}/statuses/{id}`. Объект, у которого документа
никогда не было, для неё недостижим **навсегда**, сколько бы она ни
работала. Логи это подтверждают: в окне 16.07 09:22–10:08 и 23.07 20:43,
когда заливались сироты, вызовов функции нет вовсе — документы не удалялись,
их не существовало.

Сироты — нарезка длинного видео (`..._30000.mp4`, `_60000`, `_90000`,
`_150000` — 30-секундные куски) плюс серия фото. Цикл публикации сегментов
намеренно неатомарен, и при сбое на `createStatus` уже залитый кусок
остаётся ничьим. 35 сирот = 35 разных `statusId`.

**Взгляд вбок (по требованию) — где ещё тот же порядок:**

| Путь | Имя объекта | Накопление |
|---|---|---|
| статусы | уникальное на загрузку | **не ограничено** — 35 шт / 110 МБ |
| медиа чата | уникальное на загрузку | **не ограничено** — 3 шт / 2.5 МБ, свежие |
| аватар | фиксированное `avatars/{uid}.jpg` | ограничено 1 на пользователя, перезаписывается |
| фото группы | фиксированное `groups/{chatId}/avatar.jpg` | ограничено 1 на группу, перезаписывается |

То есть порядок «файл раньше документа» универсален, но течёт только там,
где имя уникально на каждую загрузку. Аватары и фото групп самоограничены по
построению — чинить нечего.

**Следствие для плана:** B11 (медиа чатов), backlog статусов и половина
B19/B21 (частично залитое не удаляется при отмене) — **одна и та же
проблема**. Отменённая загрузка оставляет объект, на который не ссылается ни
один документ, то есть ровно ту же сироту. Значит и механизм нужен один:
сборщик, который удаляет объекты старше окна ожидания, на которые не
ссылается ни один документ. По принципу переносов он идемпотентен по природе
(проверка существования, потом удаление), поэтому повторный запуск и
параллельная живая загрузка ему безопасны.

### N3 закрыт не переносом, а упразднением счётчика

Задача звучала как «перенести `mediaImageCount` на сервер», и обе её
половины упирались в одно: инкремент не идемпотентен, поэтому пока живы
старые сборки, любой перенос даёт двойной учёт или недосчёт, а
флаг-маркер версии в схеме признан хуже самой проблемы.

Разрешилось тем, что считать оказалось нечего. Число читал ровно один
потребитель — трейлинг у плитки «Media, keçidlər və sənədlər», причём
нажатие на неё до сих пор заглушка. Ради этого числа на КАЖДУЮ
отправленную фотографию уходила отдельная запись в `chats/{chatId}` — в
тот самый документ, ради которого превью свели в одну транзакцию (B16), а
слушателей — в одного (B17).

Теперь число берётся двумя агрегатными запросами на том экране, который
его показывает: `count(type == image)` минус `count(type == image &&
deletedForAll == true)`. Вычитание — потому что «не удалено у всех» в
Firestore не выражается: у большинства сообщений поля нет вовсе, а запрос
по отсутствующему полю не находит ничего. Итог: точное число за одно-два
чтения, минус запись на каждую фотографию, и ни поля, которое может
разъехаться, ни миграционного окна, ни пересчёта.

Соседняя плитка «Seçilmişlər» в том же файле считала так с самого начала.

### Правка A2 + N16 + N17 (одной работой) — что сделано

Согласованный жизненный цикл раунда: он теперь завершается **двумя**
путями — согласием и отменой, а не одной только отменой.

| Состояние | Условие | Инициатор | Получатель |
|---|---|---|---|
| Раунда нет | `jobOfferBy == null` | кнопка «İş təklif et» | то же |
| Предложено, даты нет | есть предложение, нет даты, нет согласия | «Tarix seç» + «İmtina» | **серая** «Razıyam» + «İmtina» |
| Ждёт дату | + `waitingForDateAt != null` | + «🤝 cavab gözləyir» | то же |
| Дата предложена | `eventDate != null`, нет согласия | «Tarix dəyiş» + «İmtina» | **золотая** «Razıyam» + «İmtina» |
| **Согласовано** | `recipientAgreed == true` | **плашки нет**, кнопка вернулась | то же |
| Отменено | `cancelledBy != null`, `jobOfferBy == null` | плашки нет, кнопка вернулась | то же |

**Как сделано.** Один выводимый признак
`jobOfferRoundOpen = jobOfferBy != null && !recipientAgreed` заменил две
независимые проверки `jobOfferBy != null` в трёх местах: плашка, кнопка
«İş təklif et» в шапке, throttle записи «печатает».

Три решения, которые важно не переиграть:

1. **Признак на `recipientAgreed`, а не на серверном `completed`** —
   первый относится к текущему раунду (его сбрасывает `setJobOffer`) и
   виден обеим сторонам мгновенно, не дожидаясь Cloud Function.
2. **Поля не очищаются.** `recipientAgreedAt` — durable-триггер
   поздравительного окна: сотрёшь его, и окно молча потеряется у того,
   чей экран не был открыт. А защита от второго договора на ту же сделку
   устроена в `onChatUpdated` как `before.recipientAgreed === true →
   выход`, то есть сброс флага разрешил бы дубль.
3. **N17** — `saveChatEventDate` теперь пишет ещё и
   `waitingForDateAt: null`: причина напоминания исчезла вместе с
   выбором даты. Повторного окна это не создаёт, показ гасит отметка
   `negotiationSeenAt`.

**A2** получил подтверждение в том же виде, что у «Çatı təmizlə»,
и спрашивает всегда: после N16 «İmtina» отменяет только **открытый**
раунд, значит терять есть что в любом случае.

### Судьба поля `completed` — удалено целиком

Разобрано по требованию: мёртвое поле, которое сервер пишет каждый раз,
— будущая ловушка. Факты: писал клиент при создании чата и
`onChatUpdated` после сделки, разбирала `Chat.completed`, **не читал
никто и никогда**. Признаком раунда быть не могло — `setJobOffer` его не
сбрасывает, поэтому после первой же сделки оно навсегда `true`.

Осталось от свёрнутой схемы «завершённый чат форкается в новый»
(парность с mugam-v2), отменённой после живой проверки. Удалено из
клиента (создание чата, проекция `watchChatMeta`, модель) и из функции
— заодно ушла лишняя запись в горячий документ. В `firestore.rules`
поле упоминалось только в комментарии, валидации на нём нет.

**Остаток:** у семи существующих документов чатов значение `completed`
осталось лежать. Ничто его не читает, но в консоли Firestore оно
выглядит живым — предложено удалить разовым скриптом, решение за
владельцем.

Заодно исправлен **врущий комментарий** в `onChatUpdated`: он утверждал,
что `cancelChat` пишет `completed: true`, чего в коде клиента не было
никогда.

Список шагов, а не пометка. Экран Teymur проверяется полностью — за
получателя можно сыграть записью с сервера (`recipientAgreed: true`), и
это честно проверяет инициатора, но **экран Рафаэля этим не проверен**.

### N16 — плашка не закрывается после состоявшейся сделки 🟠

Найдено на устройстве 02.08, в реестре не значилось. Плашка переговоров
показывается, пока `jobOfferBy != null`. Это поле очищают **только два**
пути: `setJobOffer` (новый раунд) и `cancelChat` («İmtina»). Согласие его
не трогает — `acceptJobOffer` пишет только `recipientAgreed` и
`recipientAgreedAt`.

Следствие наблюдалось вживую: после состоявшейся сделки плашка остаётся
висеть у обеих сторон, и единственная кнопка, которая её убирает, — это
«İmtina». То есть интерфейс **вынуждает** нажать ровно ту кнопку, чья
опасность описана в A2, а она стирает 10 полей переговоров, оставляя
созданный договор в «Müqavilələr». Чинить вместе с A2: нужен путь
завершения раунда, отличный от отмены.

### N17 — статусная строка инициатора залипает после раннего тапа 🟡

`waitingForDateAt` никто не очищает до конца раунда: `saveChatEventDate`
пишет только четыре поля события. Гасит повторное окно отметка
«просмотрено», а не сброс поля. Но статусная строка плашки инициатора
проверяет это поле **первым**:

```
(инициатор && waitingForDate) ? '🤝 cavab gözləyir'
                              : (печатает ? '✍️ yazır...' : (прочитал ? '👁 baxdı' : '⏳ hələ baxmayıb'))
```

Значит с первого раннего тапа и до конца раунда инициатор видит только
«🤝 cavab gözləyir», а «печатает» и «прочитал» для него перекрыты.
Подтверждено данными прогона: `waitingForDateAt` оставался непустым от
08:20:44 до согласия в 08:27:55.

### A2 подтверждён вживую + асимметрия, которой не было в реестре

«İmtina» на Teymur сбросил **10 полей одним тапом без подтверждения** —
предложение, дату, тип, место, заметки, согласие и обе отметки просмотра,
причём негоциация была уже полностью согласована. Кнопка стоит вплотную к
«Tarix dəyiş». Это ровно A2, но теперь как наблюдение, а не гипотеза.

**Новое:** созданный при согласии `personalEvent` отменой **не
удаляется**. После «İmtina» в чате не остаётся следов переговоров, а
подписанный договор продолжает жить в «Müqavilələr». Возможно, так и
задумано (сделка состоялась), но развилка нигде не описана — решить при
работе над A2.

### N4 воспроизведён вживую — пропавшее окно из-за смешения шкал

Случайно и наглядно, 02.08. Скрипт игры за получателя записал
`recipientAgreedAt` по UTC (`05:11:44`), тогда как приложение пишет
**локальное** время — отметка «просмотрено» у инициатора стояла на
`09:07:31`. Условие показа поздравительного окна — «сигнал новее того,
что я уже видел», то есть `05:11 > 09:07` → **ложь**, и окно у инициатора
не появилось вовсе. У получателя оно показалось только потому, что его
отметки не было и любое время оказалось «новее».

Это ровно предсказанный N4 отказ, но не в рассуждении, а на живых
экранах: два участника, пишущие в одно поле по разным шкалам, теряют
сигналы молча. Сегодня он скрыт тем, что оба телефона в одном поясе —
разницу в четыре часа создал сторонний инструмент. Аргумент за то, чтобы
чинить N4 разом по всем девяти полям.

### Ещё находка по ходу: индикатор прочтения показывается обеим сторонам

Строка «hələ baxmayıb / baxdı» рисуется в плашке у обоих участников, хотя
осмыслена только у инициатора: получателю она сообщает, «прочитал ли
инициатор», — но тот сам это предложение и создал. Кандидат в косметику
Этапа 6.

### N4 — разбор и правка 02.08

**Целевая семантика: UTC-строка ISO-8601 с `Z`.** Определение живёт в
одном месте — `lib/core/time/instant_iso.dart`, там же полное
обоснование. Коротко, почему не `FieldValue.serverTimestamp()`, хотя оно
авторитетнее: серверная метка это сентинел (до подтверждения клиент видит
`null`), а отсечка `clearedBy` читается **синхронно до первого кадра** —
на этом построена защита Этапа 4, и пустое значение вернуло бы туда
состояние «не знаю», которое оттуда убирали (N13). Плюс сменился бы тип
на проводе и сломался офлайн.

**Переведены (10):** `clearedBy.{uid}`, `lastReadAt.{uid}`,
`deliveredTo.{uid}`, `typing.{uid}`, `negotiationSeenAt.{uid}`,
`jobOfferAt`, `waitingForDateAt`, `recipientAgreedAt`, `deletedAt` и
найденный взглядом вбок `pushTokens.updatedAt`.

**Чтение не правилось** — `DateTime.tryParse` даёт верный момент для
строки с `Z`, а `isAfter`/`difference` сравнивают абсолютные мгновения.
**Отображение правилось**: `_formatInfoTime` получил `.toLocal()`, иначе
время доставки и прочтения рисовалось бы по UTC.

#### Необратимое последствие, которое эта правка закрывает

`deletedAt` — единственное поле класса, за которым стоит **безвозвратное
удаление**: по нему заводится таймер на 5 минут, после которого
вызывается `deleteMessagePermanently`, причём таймер работает у **обеих**
сторон и срабатывает тот, чей раньше. При читателе западнее писателя
разница уходит в минус, `remaining` становится нулём — и документ
сообщения удаляется **немедленно вместо пяти минут**. Остальные девять
дают только косметику (индикаторы «baxdı», «yazır...», однократно
пропущенное окно раунда).

#### Переходное окно оказалось безопасным — и вот почему

Проверено по каждому направлению, вывод против ожидания:

| Писатель | Читатель | Итог |
|---|---|---|
| старая сборка (без смещения) | новая, **тот же пояс** | верно: строка без смещения читается как локальная, пояса совпадают |
| новая (UTC с `Z`) | старая сборка | верно: `Z` понимают обе |
| разные пояса | | неверно — но это **существующая** болезнь, а не следствие правки |

То есть смешение форматов само по себе ничего не ломает: ломает
расхождение поясов, и правка его как раз убирает. Отдельной защиты
переходному окну не понадобилось.

#### Миграция: только `clearedBy`, 3 значения

Мигрировано именно оно, потому что это **единственное поле, которое
сравнивается годами** — отсечка истории чата, живёт до следующей чистки.
Остальные девять сравниваются с `now()` в окне секунд-минут либо живут
внутри одного раунда (`setJobOffer` обнуляет `negotiationSeenAt`) — они
устаревают сами.

Переведено с допущением «записано по стенным часам Баку» (UTC+4
круглый год, переход на летнее время отменён в 2016) — это ровно то
допущение, при котором значения работали до сих пор:

| Было | Стало |
|---|---|
| `2026-08-02T01:26:21.293548` | `2026-08-01T21:26:21.293Z` |
| `2026-08-02T03:11:08.793922` | `2026-08-01T23:11:08.793Z` |
| `2026-08-01T20:07:38.185414` | `2026-08-01T16:07:38.185Z` |

**Момент не изменился ни у одного** — поменялась только запись. Повторный
прогон находит ноль кандидатов.

#### Версия локального ключа: v3 НЕ нужен

Вопрос стоял так: на устройствах в блобе `mugam_msg_cleared_v2` лежит
старое значение, сервер теперь отдаёт новое. Разбор:

- миграция сохраняет **момент**, а старую строку устройство и так читает
  как локальную в том же поясе — оба представления дают одно и то же
  мгновение, поведение не меняется даже до обновления блоба;
- живой слушатель приносит новое значение, `setClearedAt` перезаписывает
  диск сам (сравнение строк там же вызывает ровно одну лишнюю запись);
- `toIso8601String()` при перезаписи сохраняет `Z`, если значение пришло
  в UTC, — на диск ложится та же семантика, что в Firestore.

Смена версии ключа означала бы «забыть отсечку и узнать заново», то есть
окно «не знаю» на ровном месте. Не нужно.

#### Запрет: `eventDate` и дата договора к общей семантике НЕ приводить

Есть второй класс времени — **плавающее гражданское**: `eventDate` на
документе чата и `date` у `personalEvents`. Это не момент на оси, а
запись в календаре: тədbir в 20:00 остаётся в 20:00 там, где он
проходит, независимо от того, в каком поясе сейчас смотрящий. Перевод в
UTC сдвинул бы показанное время при поездке — то есть **создал бы баг
там, где его нет**.

Оба места помечены комментариями в коде. **При будущей уборке «привести
всё к единой семантике» эти два поля не трогать** — единообразие здесь
ложная цель, и именно так его однажды и сломают.

### A3 — замер 02.08 показал, что задача не та, что записана

Перед слиянием функций снят замер вызовов за сутки:

| Функция | Вызовов за 24 ч |
|---|---|
| `onChatUpdated` | 32 296 |
| `onJobOfferWaitingForDate` | 32 288 |
| `onNewMessage` | **458** |

То есть на каждое отправленное сообщение приходится **около семидесяти**
обновлений документа чата — примерно 22 записи в минуту круглые сутки, в
проекте с семью чатами и пятью пользователями.

**Следствие для задачи.** A3 записан как «две функции на один документ,
обе поднимаются на каждую запись», и слияние действительно уполовинит
вызовы. Но само число 32 тысячи говорит, что главная стоимость не в
количестве функций, а в том, **кто и зачем так часто пишет в горячий
документ**. Слить функции, не разобрав причину, — значит убрать
показания приборов, оставив болезнь: это тот же документ, ради которого
превью свели в одну транзакцию (B16), а трёх слушателей — в одного
(B17), и по которому уже был подтверждён write-шторм (~20 записей/с,
~2000 вызовов за 5 минут, см. комментарии в chat_screen.dart).

**Начинать со следующего:** найти писателей `chats/{chatId}` и разложить
32 тысячи по источникам (кандидаты: `typing.{uid}` каждые ~3 с при
наборе, `deliveredTo`/`lastReadAt` на каждое открытие, `activeUsers` при
входе-выходе с экрана, превью от `onNewMessage`). Только после этого
решать, что сливать и что убирать.

#### Разбор 02.08: это была петля, и она уже мертва

Вместо суточного среза взята неделя с разрезом по часам и минутам.

| День (UTC) | Обновлений `chats/*` | Сообщений | На сообщение |
|---|---|---|---|
| 30.07 | 197 484 | 75 | 2633 |
| 31.07 | 70 701 | 113 | 626 |
| 01.08 | 42 109 | 205 | 205 |
| **02.08** | **340** | **38** | **8,9** |

Суточный замер, с которого начинался A3, попал на хвост события, а не на
норму. Пик — 74 498 обновлений за час в ночь на 31.07 (02:00 по Баку),
при **нуле** отправленных сообщений в тот час.

Минутный разрез этого часа опознаёт природу однозначно: ровное плато
**2400–2700 записей в минуту (40 в секунду) двадцать три минуты подряд**,
включается за одну минуту и обрывается в ноль за одну. Так не выглядит
нагрузка от людей — так выглядит петля обратной связи «слушатель
документа → запись в тот же документ → слушатель». Ровно её частный
случай уже был пойман 01.08 вживую (~7 записей/с с одного устройства,
`markChatAsReadBy` с одним и тем же `lastMsgId` и новым
`DateTime.now()`) и закрыт гвардом `_lastMarkedReadMsgId`
(chat_screen.dart, коммит 6175ac1).

**Чего установить не удалось — и это главный урок.** Перелом трафика
приходится на 01.08, 18:40 по Баку; гвард закоммичен в 23:47 того же дня.
Сборки на устройство ставились раньше коммитов, так что версия
«оборвал гвард» правдоподобна — но **доказать её постфактум нечем**: в
окне перелома на устройства попало несколько сборок подряд (B17 —
слушатели документа чата, B16 — превью одной транзакцией), а счётчик
вызовов функции не знает, какое поле писалось.

**Отсюда правка:** в `onChatUpdated` заведён постоянный сторож — одна
строка `[chat-write] <chatId> <изменившиеся поля>` на каждое обновление.
Это не диагностика Этапа A5, снимать её вместе с ней нельзя (помечено
комментарием в коде). Стоимость в спокойные сутки — ~340 строк;
возврат петли виден как один и тот же набор полей десятки раз в секунду,
то есть следующий такой случай стоит одного `grep`, а не недели догадок.

**Побочный факт, проверенный пробой:** Firestore **не** порождает событие
`onDocumentUpdated`, если запись не изменила содержимое документа
(четвёртая запись пробы, тем же значением, не подняла функцию вообще).
Значит все 310 тысяч обновлений за неделю были настоящими изменениями
данных — то есть кто-то писал свежую отметку времени, а не повторял
одно и то же.

#### Решение по исходной формулировке: функции не сливать (A3)

`onJobOfferWaitingForDate` развёрнут только 31.07 и с 01.08 идёт ровно
вровень с `onChatUpdated` (42 109 против 42 109; 340 против 340) — то
есть каждое обновление документа чата действительно стоит двух вызовов.
Но при нынешних 340 обновлениях в сутки это 680 вызовов против
бесплатного лимита в 2 млн в месяц: экономия от слияния — ноль, а цена —
потеря изоляции между работающим путём «согласие → PersonalEvent» и
путём push-напоминания (сейчас исключение в одном не мешает другому;
причина разделения записана в комментарии над функцией).

Настоящая стоимость была в петле — 310 тысяч **записей** Firestore за
неделю, это вдвое выше бесплатного суточного лимита, — и она устранена.
Мерой остаётся сторож: если отношение «обновлений на сообщение» снова
уйдёт с 9 к сотням, лог сразу назовёт поле.

### A5 — что дала временная диагностика (записано ДО её снятия)

Диагностика снимается последней, но вместе с ней уходят и комментарии, в
которых лежали её выводы. Здесь они сохранены отдельно от кода.

| Счётчик | Что измерял | Что установил |
|---|---|---|
| `debugBuildCount` / `debugDisposeCount` (контроллер) | не пересоздаёт ли Riverpod `autoDispose` контроллер чаще, чем живёт экран | **пересоздания нет** — версия «шторм от пересоздания подписок» отвергнута замером |
| `debugWidgetInitCount` / `debugWidgetDisposeCount` (экран) | не рвётся ли `_ChatScreenState` быстрее, чем видно снаружи (`dispose`+`initState` внутри одного кадра) | **не рвётся**; заодно закрыт вопрос, почему гвард в поле экрана мог бы обнуляться |
| `debugMarkReadGuardPassed` / `Blocked` | сколько раз гвард расписки пропустил и сколько заблокировал | сверялось с числом настоящих сетевых вызовов |
| `debugMarkChatAsReadByCallCount` | сколько раз метод записи реально вызван | **приём, который стоит унести:** счётчик на месте РЕШЕНИЯ и счётчик на месте ЗАПИСИ должны совпасть; расхождение означает, что лишние вызовы приходят из другого места, а не из проверяемого |
| `debugLastSetJobOfferError` | текст исключения `setJobOffer`, который `try/catch` глотал молча | **исключений не было ни разу** — значит «предложение не долетает» было не про ошибку записи; настоящая причина нашлась потом (переустановка приложения посреди раунда) |
| `_debugLastMetaSignature` + плашка | какие изменения `chatMeta` реально доезжают до ЭТОГО устройства | показало, что поток доставляет всё; расхождение было в интерпретации, а не в доставке |

**Условия наблюдения на этих устройствах — durable-факт, не деталь
одного дня.** `debugPrint` на боевой сборке физического телефона не
виден, Crashlytics в реальном времени не запрашивается. Поэтому
единственный способ увидеть внутреннее состояние — вывести его **на
экран**. Отсюда и плашки, и статические счётчики: обычная отладка здесь
недоступна, и это надо закладывать в план проверки заранее.

> **Уточнение 03.08, вечер — посылка верна, вывод был шире посылки.**
> Первая половина («на боевой сборке `debugPrint` не виден») — верна,
> релиз его вырезает. Но **«единственный способ» неверно**: это правда
> только про релиз, а не про устройства как таковые. При **отладочной**
> сборке с прицепленной сессией `flutter run` логи с телефона видны
> прямо в её выводе — замерено в тот вечер, причём на **беспроводном**
> Teymur, то есть транспорт делу не мешает:
>
> ```
> flutter: 🟢 PresenceService.start(1IBr5oqcHCUZRpkpE4lGyPAKBNn2)
> flutter: [CALLKIT] ensureListening called, _listening=false
> flutter: ----------------FIREBASE CRASHLYTICS----------------
> flutter: The following exception was thrown FirestoreService: …
> ```
>
> Видны не только свои строки, но и исключения со стеком — то есть
> ровно то, чего «наблюдение через экран» дать не может.
>
> **Чем это меняет метод, а не только запись.** Утверждение читалось как
> «на этих устройствах логов не бывает в принципе», и из-за него
> диагностика по умолчанию шла вслепую там, где логи были доступны одним
> флагом. Правильная развилка теперь такая:
>
> | Что нужно | Чем собирать | Чем наблюдать |
> |---|---|---|
> | проверки «вдвоём», живые экраны, долгие сценарии | **релиз** | только экран (логов нет) — исходная запись верна |
> | диагностика: исключение, стек, порядок вызовов | **debug + прицепленная сессия** | лог `flutter run` |
>
> Цена второй строки записана в блоке сборки конспекта и не бесплатна:
> отладочная сборка не живёт с иконки и не даёт держать две трубки
> одновременно. То есть логи покупаются потерей второго телефона —
> выбирать по задаче, а не по привычке.
>
> **Почему эта ошибка дороже обычной:** утверждение про условия
> наблюдения определяет не ответ, а **способ искать ответ**. Неверная
> запись о поле уводит на один шаг; неверная запись о том, чем вообще
> можно смотреть, отменяет целый инструмент — и молча, потому что
> отсутствие логов выглядит как свойство устройств, а не как следствие
> выбранного флага.

**Урок про саму диагностику, оплаченный потерянным прогоном.**
Периодическая плашка со счётчиками появлялась каждые 3 секунды и
**перекрывала поле ввода** — печатать и отправлять во время проверки
стало невозможно. Таймер пришлось отключить.

> Диагностика на экране не должна занимать место, нужное для
> проверяемого действия. Иначе она отменяет тот самый сценарий, ради
> которого её ставили.

Тот же класс, что «не переустанавливать приложение внутри проверяемого
сценария» (A1): инструмент наблюдения меняет наблюдаемое.

### B18 — отметка доставки не привязана к сообщению

Формулировка в аудите («`markChatAsDelivered` только в `initState`»)
описывает следствие. Причина глубже: `deliveredTo.{uid}` хранит **время
последнего открытия чата**, а галочка проверяет это поле на `!= null`.
То есть вторая (серая) галочка означает не «сообщение доставлено», а
«собеседник когда-то заходил в этот чат». Это ровно тот же класс, что
B28, только `readBy` был мёртвым, а это поле показывается пользователю.

Доказательство из боевых данных, группа «111»:

```
последнее сообщение          2026-08-02T14:11:56Z
deliveredTo[6s4Ffvkh…]       2026-08-02T05:52:03Z   ← на 8,3 часа РАНЬШЕ
```

Отметка старше сообщения на восемь часов — а «доставлено» под этим
сообщением всё равно горит.

**Варианты и цена.** Требование «не чинить одно, добавляя нагрузку в
горячий документ» (A3) здесь решающее:

| | Что делает | Записей в `chats/{chatId}` | Чинит ли причину |
|---|---|---|---|
| **A** | звать `markChatAsDelivered` ещё и на новые сообщения при открытом экране | +1 на каждое входящее | нет — поле остаётся временем, при закрытом чате врёт по-прежнему |
| **B** | ввести `deliveredSeq.{uid}` по образцу `lastReadMsgId.{uid}`, писать из списка чатов по `lastMessageSeq` | ≤1 на **пачку** новых сообщений, сходится | да |
| **D** | убрать серую галочку совсем, оставить «отправлено» и «прочитано» | 0, минус существующие | да — врать становится нечем |

Рекомендация — **B**: он единственный делает галочку правдой, а по
записям дешевле варианта A (пачка вместо сообщения) и линеен по трафику,
в отличие от петли, которую разбирал A3. Риск у него один и известный:
«снимок → запись → снимок» это потенциальная петля, поэтому запись
должна быть строго монотонной (`deliveredSeq` только растёт) плюс
локальный дедуп по `(chatId, seq)` в памяти. Сторож `[chat-write]` из A3
теперь покажет такую петлю за минуты.

Требуется переходное окно: старые сборки пишут время, новые — номер,
поэтому на время перехода галочка считается как
`deliveredSeq >= msg.seq` **или** (номера нет вовсе И время есть) —
иначе у всех разом пропадут серые галочки.

#### Выбран вариант B — что именно сделано

Пишет отметку `_recordDeliveries` в `watchChats`, а не экран чата:
список чатов — единственное место, где устройство узнаёт о новом
сообщении, **не открывая переписку**. Это и есть смысл слова
«доставлено».

Защита от петли «снимок → запись → снимок» тройная, и каждый слой закрывает
свой зазор:

1. **Сходимость.** После записи `deliveredSeq == lastMessageSeq`, и
   условие записи перестаёт выполняться само. Петля не может себя
   поддерживать.
2. **Кэш в памяти** (`_deliveredSeqWritten`). Закрывает окно между
   отправкой запроса и приходом снимка с результатом — пока оно открыто,
   условие ещё истинно, и пачка снимков породила бы пачку одинаковых
   записей. Ровно из такого механизма вырос write-шторм из A3.
3. **Откат кэша при ошибке**, иначе одна неудачная запись навсегда
   закрыла бы чат от повторной попытки в этой сессии.

#### Переходное окно: кто что видит, пока живут обе сборки

Новая сборка **продолжает писать `deliveredTo`** (`markChatAsDelivered` в
`initState` не тронут) и дополнительно пишет `deliveredSeq`.

| Смотрит | Собеседник на новой сборке | Собеседник на старой |
|---|---|---|
| **Новая сборка** | правда: галочка по номеру | как раньше, включая прежнюю ложь — но галочка не пропадает |
| **Старая сборка** | как раньше | как раньше |

То есть компромисс окна ровно один: **правда появляется парами**. Пока
обе стороны не обновились, отправитель видит прежнее поведение, а не
пустоту. Ничего не ломается ни в одном из четырёх сочетаний.

**Сколько длится:** до обновления последнего устройства. Сейчас это
Teymur (обновлён) и Rafael (сборка без B18, устройство недоступно), плюс
mugam-v2 из обихода выведен.

#### Отложенный шаг I4 по `deliveredTo` — с условием, а не «потом»

Удаление старого поля из кода и из данных откладывается **до закрытия
окна**, потому что раньше оно погасит галочки у необновлённых сборок.

**Условие закрытия, проверяемое зондом** (оба пункта):

1. Ни одного чата, где для участника есть `deliveredTo`, но нет
   `deliveredSeq`, при `lastMessageSeq > 0`.
2. С момента обновления последнего устройства прошло ≥ 7 суток (запас на
   участника, который просто давно не открывал приложение).

**Что делать по закрытии:** убрать запасную ветку из
`deliveryStatusFor`, перевести или удалить `markChatAsDelivered`, удалить
поле `deliveredTo` из документов и из перечисления в `firestore.rules`.

### N19 — присутствие получило срок годности

**1. При каких условиях пуш не доходил (на данных, не по коду).**
Сервер молчит для всех, кто числится в `chats/{id}.activeUsers`. В проде
нашёлся чат, где `1IBr5oqc…` числился «сейчас в чате» при последнем
сообщении **54,7 часа назад**, находясь в это время в другом месте
приложения. То есть любое сообщение в тот чат ушло бы без уведомления.
Косвенное подтверждение того же: при повторном снятии зонда минутой позже
человек уже числился в двух чатах разом — состояние, невозможное
физически.

**2. Как отметка убиралась.** Проверены четыре пути:

| Событие | Убиралась? |
|---|---|
| выход с экрана чата | да, `removeActiveUser` в `dispose` |
| сворачивание приложения | **нет** — `dispose` не зовётся |
| убийство приложения | **нет** |
| обрыв сети | **нет** — запись просто не уходит |

Три из четырёх путей оставляли отметку навсегда, и это самые обычные
способы закончить работу с приложением.

**3. Починено по образцу `deliveredSeq`: у признака появился момент.**
Присутствие здесь нужно по существу — вопрос «смотрит ли он сейчас», а не
«был ли когда-то», — поэтому вместо отметки без срока годности признак
переехал в `users/{uid}` рядом с сердцебиением присутствия. Срок годности
там есть по построению: `lastSeen` обновляется раз в 60 с, пока приложение
на переднем плане, и перестаёт — как только оно свёрнуто, убито или без
связи. Окно 2 минуты, ровно как у `User.isActuallyOnline` на клиенте.

Побочно это снимает нагрузку, а не добавляет: сердцебиение уже писалось,
а `activeUsers` — 11% всех записей в горячий документ по разбивке A3 —
после закрытия переходного окна уходит совсем.

**4. Обратная сторона проверена отдельно.** Лишний push раздражает
сильнее, чем пропущенный, поэтому тестами закреплено: человек, который
действительно смотрит в чат, уведомления не получает — включая случай
одного пропущенного удара сердца (окно вдвое больше интервала). При
ошибке чтения документа функция считает, что человек НЕ смотрит: лишний
push заметен и поправим, потерянный не заметен никем.

**5. Переходное окно.** Новая сборка пишет `activeChatId` **всегда**, в
том числе как `null` — по отсутствию самого ключа сервер и отличает
старую сборку.

| Получатель | Что происходит |
|---|---|
| новая сборка | решает `activeChatId` + свежесть; застрявший `activeUsers` больше не заглушает |
| старая сборка | прежнее правило по `activeUsers` — иначе она начала бы получать push, пока человек сидит в чате |

Длится до обновления последнего устройства. Пока оно не закрыто, старая
сборка сохраняет и старый дефект — это осознанный размен: сломать ей
поведение хуже, чем оставить как было.

Решение вынесено в `functions/src/presence.ts` чистой функцией и покрыто
11 тестами без эмулятора. Причина именно такая: цена ошибки тут
несимметрична и невидима — потерянный push не замечает ни отправитель, ни
получатель, ни лог.

**Отложенный шаг I4:** после закрытия окна убрать `addActiveUser`/
`removeActiveUser`, само поле `activeUsers` из документов и ветку старого
правила на сервере. Условие закрытия то же, что у B18-cleanup.

остаётся версией. На вывод по N19 это не влияет: проверялось, что после
прекращения ударов отметка протухает, и это подтверждено трижды.

Живых iOS-токенов в проекте нет ни одного (см. N20), поэтому «пришёл ли
push» проверить нечем — проверялась та половина, которая была сломана и
наблюдаема. Доставка вынесена отдельным пунктом в Этап 7, чтобы не
раствориться в общей формулировке про пуши.

### Окно подавления push сужено с 60–120 с до 30–60 с

Прогон дал число, которого раньше не было: после ухода из приложения
push подавляется **ещё 60–120 секунд**. Окно 120 с отсчитывается от
последнего удара, а он был до 60 с назад — то есть человек, свернувший
приложение и получивший сообщение через минуту, уведомления не увидит.

Сужено учащением сердцебиения до 30 с **только при открытом чате**:
свежесть решает единственный вопрос — «смотрит ли он сейчас в ЭТОТ
чат», и задаётся он лишь когда `activeChatId` совпал. Цена — 2 записи в
минуту в `users/{uid}`; документ чата, вокруг которого крутится весь A3,
не затрагивается вовсе.

**Связки «обнови сервер и все сборки разом» намеренно нет.** Сборка
объявляет свой интервал сама (`presenceIntervalMs`), сервер берёт
двойной от объявленного и зажимает в границы 30–120 с; поля нет —
работает прежнее окно 120 с. Тот же приём, что с ключом `activeChatId`:
отсутствие поля само является сведением о сборке. Иначе сборка с редким
ударом начала бы получать push прямо во время чтения чата — та самая
несимметричная цена, ради которой решение вынесено в чистую функцию.
Закреплено 19 тестами (было 11).

### N20 — один push-токен на несколько аккаунтов 🟠

Найдено при подготовке проверки N19: прежде чем слать push, стоило
посмотреть, **кому** он уйдёт. Пятый случай класса «визит вместо
события».

**Что в данных прода 02.08.** 9 документов токенов у 6 пользователей, а
различных токенов — 5. Три токена лежат под несколькими аккаунтами
сразу:

```
cp4Li9rVRyKp…  →  Teymur, Rafael, Ramil      (id документа SKQ1.220303.001)
e8olZ1RrRLOI…  →  Rafael, Ramil              (id документа AP3A.240905.015.A2)
e3DoPD60RmyY…  →  Rafael (BP2A.250605.031.A3), Muhammed (AP3A.240905.015.A2)
```

**Причина — id документа не идентифицирует устройство.** На Android
бралось `androidInfo.id`, а это идентификатор **сборки операционной
системы**. Данные показывают обе стороны ошибки сразу:

1. **Разные устройства сливаются в один документ** — все телефоны с
   прошивкой `SKQ1.220303.001` пишут в одну и ту же запись. Push,
   адресованный одному человеку, уходит на устройство, где сидит другой,
   а в теле push'а — **имя отправителя и начало сообщения**. Это утечка
   личных данных между аккаунтами, тот же класс, что L1.
2. **Одно устройство расползается по разным документам** — третья строка
   выше: один токен под двумя разными id, потому что телефон обновил
   прошивку между входами. Прежняя запись остаётся сиротой навсегда.

Второй причиной было то, что `unregisterToken` существовал в коде, но
**не вызывался ниоткуда**: при выходе из аккаунта токен оставался лежать
у прежнего владельца.

**Мёртвые токены не удалялись и продолжали получать отправки.** Замер по
логам: 673 неудачных отправки за 30 дней, из них 64 за одни сегодняшние
сутки, все — `registration-token-not-registered`. Проверка вхолостую
(`dryRun`, ничего не доставляет) показала: из пяти различных токенов
**три мертвы**, и держат их 7 документов из 9. Мертвы ровно те три,
которые делились между аккаунтами.

**Заодно установлено, что iOS-токенов нет вовсе.** Все id — Android-
отпечатки сборок, самый свежий токен от 24.07; два iPhone под тестом не
зарегистрировали ни одного. Это согласуется с тем, что пуши на iOS
выключены за отсутствием платного аккаунта Apple: `getToken()` без
APNs-права падает, а `registerToken` глотает исключение молча.

**Что сделано:**

| Требование | Как закрыто |
|---|---|
| id идентифицирует устройство, а не сборку | случайный идентификатор установки в `SharedPreferences`, одна семантика на обе платформы. `identifierForVendor` на iOS не был сломан, но два разных правила для одного поля — будущая ловушка |
| прежние документы этого устройства | принцип I4: при первой регистрации новым id свои старые записи (по прошивке / по `identifierForVendor`) удаляются |
| токен снимается при выходе из аккаунта | `unregisterToken` вызывается в «Çıxış» **до** `logout()` — правила разрешают писать в свою ветку только владельцу, после выхода удалять уже нечем |
| не слать на мёртвые токены | `pruneIfTokenDead` удаляет документ ровно на двух кодах: `registration-token-not-registered` и `invalid-registration-token`. `invalid-argument` намеренно не в списке — он приходит и на испорченную полезную нагрузку, и удаление по нему стирало бы живые токены из-за нашей же ошибки |

Чинилось **сейчас, а не в день включения пушей**: код от доставки не
зависит, а отложить — значит гарантировать, что в день включения утечка
заработает у всех разом.

#### Третий путь, недоступный клиенту, — и почему понадобился сервер

Путей, которыми токен попадает к чужому аккаунту, оказалось три, и
клиент закрывает только два:

| Путь | Кто закрывает |
|---|---|
| id документа общий для разных устройств | клиент: id идентифицирует установку |
| выход через «Çıxış» | клиент: `unregisterToken` до `logout()` |
| **смена аккаунта БЕЗ явного выхода** | **только сервер** |

Третий недоступен клиенту принципиально: сессия отозвана сервером,
токен истёк при убитом приложении, устройство восстановлено из копии —
приложение просыпается уже под другим аккаунтом, а запись прежнего
владельца удалить нечем, потому что правила разрешают писать в
`users/{uid}/pushTokens` только самому владельцу. Это ровно те случаи,
ради которых в `main.dart` существует
`_reconcileLocalStoreWithSignedInUid`, и, судя по данным, именно так три
токена и разошлись по нескольким людям.

Закрыто триггером `onPushTokenWritten`: при регистрации токена он
снимается со всех прочих владельцев. Идемпотентен по природе — проверка
существования, потом удаление, — то же свойство, на котором стоит
сборщик сирот.

#### Результат уборки данных 02.08

| | До | После |
|---|---|---|
| Документов токенов | 9 | 2 |
| Различных токенов | 5 | 2 |
| Мёртвых токенов | 3 (в 7 документах) | 0 |
| Токенов под несколькими аккаунтами | 3 | **0** |

Правило уборки одно и проверяемое: удаляется документ, чей токен **сам
FCM** объявил несуществующим (`dryRun` проверяет и не доставляет
ничего). **Разовый скрипт** живой токен не удаляет никогда, даже если тот делится между
аккаунтами: решать за устройство, кому оно принадлежит, задним числом мы
не вправе. Это то же правило, что у сборщика сирот: **неполное знание не
даёт права удалять**. Повторный прогон сразу после: ноль кандидатов.

Важно не спутать это с триггером: `onPushTokenWritten` **как раз
удаляет живые копии** у прежних владельцев — но только в момент, когда
устройство само заявило нового владельца регистрацией. Разница именно в
знании: у скрипта его нет, у триггера оно есть и пришло от самого
устройства.

Скрипт — `functions/src/scripts/cleanupPushTokens.ts`, без `--delete` не
пишет ничего.

#### Регулярная проверка живости — по образцу сборщика сирот

`pruneIfTokenDead` снимает мёртвый токен только когда по нему пытались
отправить; у человека, которому давно не пишут, он лежит вечно — так и
накопились 7 мёртвых из 9. Поэтому заведён `sweepDeadPushTokensDaily`,
04:35 по Баку (на 15 минут позже сборщика сирот — намеренно врозь,
чтобы прогоны не переплетались в логах).

Дешевле сборщика сирот: 5 проверок и обход крошечной коллекции против
обхода всей базы. Удаление **выключено** (`PUSH_TOKEN_SWEEP_DELETE=false`
в `functions/.env`), след каждого прогона — в
`maintenance/pushTokenSweep/runs`. Включать после того, как первый-второй
прогон покажет ровно то же, что ручной скрипт: тем же порядком, каким
включался сборщик сирот.

### N21 — время «Çatdırıldı» было отметкой визита 🟠

Замечено тестировщиком на экране «Məlumat» сразу после проверки A3:

```
Göndərildi   2 Aug, 20:37
Çatdırıldı   2 Aug, 20:38     ← позже прочтения
Oxundu       2 Aug, 20:37
```

Доставка позже прочтения — невозможное состояние. Причина: время в
строке бралось из `deliveredTo[uid]`, то есть из отметки **визита**,
которая переписывается при каждом открытии чата (в логе выше видны все
пять). B18 перевёл на номер сообщения галочки, а этот экран остался на
старом поле — и в списке работ B18-cleanup он не значился.

**Почему стало видно только сейчас** — разбор механики вынесен к методу
выше: два дефекта маскировали друг друга, пока обе отметки ехали вместе.

**Правка.** `deliveredAt.{uid}` пишется **той же операцией**, что
продвижение `deliveredSeq.{uid}` — отдельная запись стоила бы второго
обновления горячего документа (A3), а нужна она ровно тогда же.

Инвариант «доставка не позже прочтения» обеспечивается на показе, а не
только на записи, и это не косметика: две отметки пишут **разные места**
по одному и тому же снимку — расписку экран чата, доставку список
чатов, — и порядок между ними ничем не гарантирован. Получатель,
открывший чат до прихода сообщения, снова увидел бы перевёрнутый
порядок, уже по другой причине. Показывается время прочтения, а не
пустая строка: «доставлено не позже, чем прочитано» — самое точное, что
известно, а пропажа строки выглядела бы поломкой.

Тем же заходом устранено расхождение двух ответов на один вопрос: экран
считал доставку по `deliveredTo != null`, а галочки — по номеру, то есть
«Çatdırıldı» могло стоять под сообщением с одной галочкой. Теперь
правило одно.

#### N21b — вторая граница, вскрытая проверкой первой

Сценарий «получатель уже сидит в чате» дал зеркальную инверсию:
**«Çatdırıldı 21:28» под «Göndərildi 21:32»** — доставка раньше отправки.

Причина того же класса: `deliveredAt`, как и `lastReadAt`, живёт **на
чате, а не на сообщении**. Отметку доставки пишет список чатов — то
единственное место, где устройство узнаёт о сообщении, не открывая
переписку (так задумано в B18 и это верно). Но пока получатель внутри
чата, список не работает, номер не продвигается, и под новым сообщением
показывалось время **прошлой** доставки.

Данные прогона: сообщение seq=345 в 21:32:52, прочитано в 21:32:53,
`deliveredSeq` остался 344, `deliveredAt` — 21:28:41.

**Правка: время зажимается в отрезок `[отправлено, прочитано]`.** Если
отметка старше самого сообщения, она про него ничего не говорит — тогда
показывается время прочтения («доставлено не позже, чем прочитано»), а
если не прочитано, время не показывается вовсе. Строка «Çatdırıldı»
остаётся: факт доставки известен, неизвестен только момент, и пустое
место честнее выдуманной минуты.

**Место записи доставки не менялось намеренно.** Перенос в экран чата
вернул бы запись в горячий документ на каждое входящее — ровно то, от
чего уходили в A3 и B18, — а для сообщения, пришедшего при открытом
чате, момент доставки и так неотличим от момента прочтения.

Закреплено 18 тестами (`test/delivered_time_test.dart`), включая оба
наблюдавшихся случая и гонку писателей.

### Метод, которым найдены все четыре находки

Записан отдельно от результатов, потому что следующая сессия должна
поднять именно его.

Вопрос звучит так: **«эта отметка про событие или про присутствие?»**
Если поле обновляется фактом визита, а читается как утверждение о
конкретном событии — это находка, независимо от того, выглядит ли код
подозрительно.

Чтение кода по списку их не находило: каждое место по отдельности
выглядит правильным. `readBy`, `deliveredTo`, `lastReadAt`, `activeUsers`
нашлись подряд именно этим вопросом, причём последняя — самая дорогая:
три первых лгали на экране, четвёртая отменяла доставку уведомлений.

Второй приём того же рода: **у любой отметки присутствия обязан быть срок
годности.** Там, где он есть (`typing` — 5 с, `online` — 2 мин), дефекта
нет; там, где его не было (`activeUsers`), он и завёлся.

### Взгляд вбок после третьей находки одного класса

`readBy` → `deliveredTo` → `lastReadAt` — три подряд, все одной формы:
**отметка о визите выдавалась за отметку о событии**. Класс назван, метод
известен, поэтому проверены остальные поля с временем и списками
участников.

| Поле | Итог |
|---|---|
| `typing.{uid}` | чисто — читается с окном в 5 с, отметка 26-часовой давности «печатает» не покажет |
| `online` | чисто — есть `isActuallyOnline` (окно 2 мин), голого `online` в интерфейсе нет ни одного. Защита не теоретическая: в проде четверо с `online: true`, у одного `lastSeen` 310 ч назад, у другого его нет вовсе |
| `listenedBy` | чисто — список живёт в документе сообщения, то есть привязан к событию по своей природе |
| `clearedBy`, `negotiationSeenAt`, `starredAt` | чисто — все фиксируют событие, а не присутствие |
| **`activeUsers`** | **четвёртая находка, см. N19** |

Вывод о самом методе: три находки подряд дал не поиск багов, а поиск
**полей, где присутствие подменяет событие**. Четвёртая пришла оттуда же
и оказалась дороже трёх предыдущих вместе — те лгали на экране, эта
отменяет доставку уведомлений.

### Пятый и шестой случаи класса — и второй приём, который из них вырос

Счёт дошёл до шести, и последние два пришли **не от поиска**. Это и есть
главное, что стоит унести дальше.

| # | Поле | Что фиксирует на деле | Как читалось | Откуда пришло |
|---|---|---|---|---|
| 1 | `readBy` | кто когда-либо открывал чат | «все прочли последнее» | вопрос к полю |
| 2 | `deliveredTo` | когда последний раз открывал чат | «сообщение доставлено» | вопрос к полю |
| 3 | `lastReadAt` | когда последний раз заглядывал | «когда прочитал» | вопрос к полю |
| 4 | `activeUsers` | кто когда-то вошёл на экран | «смотрит прямо сейчас» | вопрос к полю |
| 5 | `pushTokens/{id}` | что на этом устройстве **когда-то входили** как X | «это устройство X» | взгляд вбок при проверке пушей (N20) |
| 6 | время в «Çatdırıldı» | когда получатель последний раз заходил | «когда доставлено» | **побочный эффект починки №3** (N21) |

**Шестой случай — механика, ради которой эта запись и делается.** Два
дефекта маскировали друг друга. Пока `lastReadAt` и `deliveredTo` ехали
вместе на каждое открытие чата, экран «Məlumat» выглядел
непротиворечиво: обе строки показывали время последнего визита, разница
между ними была секундной, и заметить было нечего. Как только A3
остановил первую отметку, вторая продолжила ехать — и на экране
появилось невозможное: **доставка позже прочтения** (20:38 против 20:37).

Отсюда приём, который дороже самой находки:

> После починки лжи посмотри на соседние показания, которые с ней
> сверялись. Согласованность двух врущих величин ничего не доказывает —
> она сама может быть следствием общей причины, и починка одной из них
> обнажает вторую.

Обратная сторона того же правила: **не спеши объявлять расхождение
регрессией правки**. Здесь расхождение появилось сразу после A3 и
выглядело как её последствие, а на деле правка ничего не сломала — она
сделала видимым то, что лгало и раньше.

### Сплошной проход по классу 02.08 — искали восьмой случай до того, как он вскроется сам

После двух подряд находок, вскрытых починкой соседа, по классу прошлись
специально, не дожидаясь следующей. Формулировка поиска: **величина
уровня ЧАТА, показанная или использованная как факт о КОНКРЕТНОМ
сообщении.** Три борозды: все поля вида `*.{uid}` в документе чата; всё,
что сравнивается с `timestamp` или `seq` конкретного сообщения; всё, что
показывается пользователю с точностью до минуты.

Из 25 полей проекции документа чата на экранах сообщений читаются 12:

| Поле | Как используется | Вердикт |
|---|---|---|
| `deliveredTo.{uid}` | запасная ветка галочек, раньше — время на «Məlumat» | находка N21, закрыта |
| `deliveredAt.{uid}` | время «Çatdırıldı» | находка N21b, закрыта |
| `deliveredSeq.{uid}` | сравнивается с `msg.seq` | чисто — число против числа, «докуда доставлено» |
| `lastReadMsgId.{uid}` | разрешается в сообщение, его время сравнивается с `message.timestamp` | чисто — «докуда прочитано» по построению |
| **`lastReadAt.{uid}`** | время «Oxundu» под конкретным сообщением | **тот же класс, но невыворачиваемый — см. ниже** |
| `unreadCount.{uid}` | бейдж и путь починки | чисто **по этому классу** — величина чата показана на месте чата. Но у поля есть свой, другой дефект: обнулять его стало нечем, см. N22. «Чисто» здесь означает «не тот класс», а не «с полем всё в порядке» |
| `negotiationSeenAt`, `recipientAgreedAt`, `jobOfferAt`, `waitingForDateAt` | сравниваются между собой | чисто — раунд против раунда (N4) |
| `members`, `isGroup`, `name` | состав, заголовок | не факт о сообщении |
| `lastMessageSeq` | сравнивается с номером свежайшего известного | чисто — обе величины про чат |

Экраны с минутной точностью — четыре: «Məlumat» (закрыт правкой),
просмотрщик вложений и пузырь сообщения (оба берут `message.timestamp`,
своё), карточка чата (`lastMessageTime` — чат на чате). Сравнений с
`timestamp`/`seq` сообщения два: `readByUid` и расчёт галочек, оба
сравнивают «докуда» по назначению.

#### `lastReadAt` — свойство с границей, а не открытая находка

Время «Oxundu» — это отметка на весь чат, показанная под каждым
сообщением. Прочитали А в 10:00, потом Б в 10:30 — «Məlumat» для А
покажет 10:30. Формально тот же класс.

Но **вывернуть его наизнанку не удаётся**, и в этом отличие от N21/N21b.
Рассуждение: строка рисуется только когда `readByUid` истинно, а это
требует, чтобы расписка называла сообщение не старше этого — значит
расписка заведомо позже прихода. Остаётся только завышение: показанный
момент **не раньше** истинного.

**Условие, при котором рассуждение верно, и замер под него.** Оно
опирается на то, что `lastReadAt` и `lastReadMsgId` пишутся **одной
операцией** — иначе время могло бы остаться от древней расписки при
свежем идентификаторе, и инверсия стала бы возможной. В коде это так
(`markChatAsReadBy` пишет три поля разом), но чужая сборка могла бы
писать иначе, поэтому проверено по данным прода 02.08, а не выведено:

| Замер | Результат |
|---|---|
| пар «расписка + её время» в базе | 3 |
| из них с инверсией (время расписки раньше названного сообщения) | **0** |
| случаев «идентификатор есть, времени нет» | **0** |
| случаев «время есть, идентификатора нет» | **0** |

Выборка мала — три пары на весь проект, — поэтому это **не** «инверсия
невозможна», а «в сегодняшних данных инверсий нет, и путь, которым она
могла бы возникнуть, в данных не наблюдается». Признак, по которому её
ловить дальше: расхождение двух отметок в логе сторожа.

Точность упирается не в ошибку, а в данные: **времени прочтения
конкретного сообщения не существует нигде**, есть одна отметка на чат.
Завести её на каждое сообщение — это запись в горячий документ на каждое
входящее, ровно то, от чего уходили в A3 и B18. Поэтому записано как
названное свойство с границей («прочитано не позже, чем»), а не как
работа.

### N22 — залипший бейдж непрочитанного, регрессия от правки A3 🔴

Найдено тестировщиком вечером 02.08, через несколько часов после правки:
число на карточке чата не обнуляется при входе в чат.

**Подтверждено данными прода сразу, до всякого разбора:**

| Факт | Значение |
|---|---|
| `lastMessageSeq` | 349 |
| `deliveredSeq` | Teymur 349, Rafael 349 — доставлено всё |
| `unreadCount` | **Teymur = 1, Rafael = 1** — при том, что непрочитанного нет |

**Механизм.** Счётчик обнуляет единственное место — `markChatAsReadBy`.
Правка A3 добавила туда гвард «расписка про это же сообщение уже
записана — писать нечего». Но у **пути починки залипшего счётчика**
идентификатор сообщения по определению тот же самый: счётчик залипает
именно на последнем входящем. Гвард глушит починку, и обнулять становится
нечем.

**Это регрессия, а не старый дефект:** до правки повторная расписка
уходила вхолостую — и попутно обнуляла счётчик. Убрав холостую запись, я
убрал и её единственную полезную работу.

**Почему это не поймали тесты и прогон.** Проверка A3 звучала как «пять
открытий — ноль записей», и она честно прошла. Никто не проверял, что
происходит, когда счётчик уже залип: для этого нужно состояние, которое
возникает от гонки с Cloud Function (B15), а не от действий человека.

**Правка (предложена, ждёт подтверждения):** развести расписку и
счётчик. У пути починки будет свой метод, пишущий только
`unreadCount.$uid = 0`. Это и семантически честнее — расписка фиксирует
событие, счётчик чинит состояние, — и дешевле: одно поле вместо трёх.

### Проверка собственных записей 02.08 — что было сказано по рассуждению

N22 вскрыл не только дефект кода, но и **неверную строку в реестре**,
написанную мной в тот же день. Поэтому по всем сегодняшним записям
прошлись отдельно, с одним вопросом: **это замерено или выведено?**

| Утверждение | Было | Стало |
|---|---|---|
| «счётчик непрочитанных этой проверкой не страдает» | выведено из «починка — отдельный путь» | **неверно**, N22; строка помечена в тексте A3 |
| «живой токен не удаляется никогда» | верно для скрипта, но читалось как общее правило | уточнено: скрипт не удаляет, триггер удаляет — и сказано, чем они отличаются (знанием) |
| «`unreadCount` — чисто» в таблице прохода | верно **по классу**, читалось как «с полем всё хорошо» | уточнено явно |
| «прочитано раньше отправки невозможно» | выведено из построения экрана | заменено на замер: 3 пары, 0 инверсий, 0 расхождений; сказано, что выборка мала |
| «телефон ушёл в неактивное состояние раньше сворачивания» | правдоподобная версия | помечено как неустановленное; у тестировщика не уточнялось |

**Правило, ради которого это записано.** Реестр читает следующая сессия
как факты, и неверная строка в нём дороже неверной строки в коде: код
падает, а запись тихо уводит по ложному следу. Отсюда:

> Утверждение в реестре либо опирается на замер, либо помечено как
> версия. Слова «не страдает», «невозможно», «чисто», «никогда»
> требуют либо цифры рядом, либо оговорки — при каких условиях это
> верно и чем проверялось.

Образец того, как надо, был в тот же день рядом: одиночные записи
`lastReadAt` (ниже) записаны как наблюдение с цифрой и явной пометкой
«гипотеза, воспроизвести не удалось». Разница между этими двумя
записями — единственное, что отделяет полезный реестр от вредного.

#### Наблюдение без вывода: одиночные записи `lastReadAt`

В логе сторожа за вечер 02.08 встречаются записи, где изменился **только**
`lastReadAt` без `lastReadMsgId`: 8 у Teymur и 5 у Рафаэля за три часа.
В контрольном прогоне после последней сборки (21:28–21:33 и 21:50–21:53)
их **ноль** — пять повторных открытий дали только `deliveredTo`, расписка
ушла ровно одна на сообщение.

Гипотеза: гвард в памяти службы сбрасывается снимком, который отправился
раньше собственной записи (`_noteRecordedReadMsgId` принимает значение из
снимка безусловно), после чего экран пишет расписку второй раз — в
документе меняется только время. **Это гипотеза, а не установленный
факт**: воспроизвести сегодня не удалось. Простая «починка» опасна —
запрет принимать снимок назад сломает самолечение после неудачной записи
и может потерять расписку совсем. Записано с цифрой и способом проверки,
без вывода.

### A3, вторая половина — разбивка по источникам

Сторож `[chat-write]` дал то, чего не мог дать счётчик вызовов: **имена
полей**. За три часа — 84 записи в `chats/*`, из них заметная доля
искусственные (десять удалений тестовых сообщений дали записи
`messageCount`). Живая картина:

| Источник | Доля | Вывод |
|---|---|---|
| прочтение (`lastReadAt`+`lastReadMsgId`+`unreadCount`) | 26% | **нашлась холостая часть, см. ниже** |
| новое сообщение (превью+счётчики одной записью) | 18% | сервер, необходимо |
| вход/выход с экрана (`activeUsers`) | 11% | нужен для подавления пушей |
| доставка, новая отметка (`deliveredSeq`) | 8% | B18, по одной на чат |
| доставка, старая отметка (`deliveredTo`) | 8% | уйдёт по B18-cleanup |
| состав группы (`members`) | 4% | не механизм: человек удалил троих участников |
| набор текста (`typing`) | 1% | троттлинг работает, оставлено намеренно |

#### Находка: расписка о прочтении уходила вхолостую

Отдельным набором видно «менялся ТОЛЬКО `lastReadAt`» — шесть записей за
три часа. То есть ни прочитанное сообщение, ни счётчик непрочитанных не
поменялись, а запись в горячий документ ушла.

Причина: гвард `_lastMarkedReadMsgId` живёт в состоянии экрана и умирает
вместе с ним. При каждом повторном открытии чата он пуст — и расписка
отправляется заново для того же самого сообщения.

**Но дороже здесь не запись, а смысл.** Отправитель видит на экране
«Məlumat» время прочтения, и оно сдвигалось на момент повторного захода:
поле показывало не когда сообщение прочли, а когда получатель в
последний раз заглянул в чат. Это ровно та подмена, что была у
`deliveredTo` (B18) — отметка о событии подменялась отметкой о визите,
только здесь она ещё и показывалась пользователю с точностью до минуты.

Правка: перед записью сверяться с уже записанным `lastReadMsgId` из
документа, а не только с гвардом в памяти.

> ⚠️ **Здесь стояло утверждение «счётчик непрочитанных не страдает — его
> обнуляет отдельный путь починки». Оно неверно, см. N22.** Путь починки
> ходит через тот же `markChatAsReadBy`, который эта правка и закрыла:
> идентификатор сообщения у него по определению тот же самый, гвард его
> глушит, и обнулять счётчик становится нечем. Утверждение было сделано
> **по рассуждению** («починка — отдельный путь»), а не проверено, и
> продержалось в реестре несколько часов, пока залипший бейдж не увидел
> тестировщик.

**Итог A3.** Петля, ради которой пункт открывали, мертва (310 634 записи
за неделю → 340 в сутки). Слияние функций отклонено по цифрам. Из
оставшихся источников один оказался наполовину лишним и при этом врущим —
и найден он не рассуждением, а именами полей в логе.

### B6 — воспроизведён на устройстве, но чинить нечего

Пункт держался на рассуждении, поэтому его смотрели глазами. С первого
раза не вышло, и неудача оказалась полезнее самой проверки.

**Первая попытка провалилась из-за неверной диагностики.** Задержка была
поставлена на `_confirmAfterDelay` (300 → 3000 мс) — то есть на путь,
который в жизни не работает. Видео показало галочки через **0,5 с** при
заданных трёх: часики снимает живой слушатель Firestore, а не
подтверждение отправки. Отсюда вырос принцип I5.

**Вторая попытка, задержка на своей ждущей строке в `_upsertOne`** (и
только на ней — задержи весь upsert, чужое сообщение приедет так же
поздно, и окно снова не поймается). Скрипт-помощник пишет сообщение «от
Рафаэля» через 1,1 с после коммита, то есть гарантированно внутрь окна.

Покадровый разбор видео (5 кадров/с):

| Время | Что на экране |
|---|---|
| 3,5–5,2 с | `B6 19:05` → `B6 19:06` → **«О» с часиками, в самом низу** |
| 5,8 → 6,2 с | **перестановка**, без анимации |
| 6,5–7,6 с | `B6 19:05` → **«О» с галочками** → `B6 19:06` внизу |

Своё сообщение (номер 332) и чужое (333) поменялись местами. Эффект
реален.

**Почему правка не предлагается.** Ждущее сообщение рисуется последним
потому, что номера у него ещё нет — номер выдаёт сервер в транзакции
коммита. Варианты «починки»:

- ставить ждущее по *ожидаемому* номеру — это лишь меняет направление
  прыжка: если чужое сообщение было закоммичено раньше моего, но пришло
  позже, оно окажется под моим и прыгнет уже оно;
- придержать чужие сообщения до подтверждения своего — задержка чужой
  переписки ради своей анимации;
- оставить неверный порядок навсегда — ложь о том, что было раньше.

То есть перестановка — это не дефект отрисовки, а момент, когда экран
узнаёт настоящий порядок. Окно в боевой сборке — те самые ~0,5 с, и
попасть в него нужно чужим сообщением ровно в этот промежуток.

**Что сделано вместо правки:** замер вписан в комментарий над
`_confirmAfterDelay`, чтобы следующий человек видел реальную картину, а
не только теоретическую; лишняя перезапись диска в `markConfirmed`
убрана проверкой состояния перед записью.

### B28 + B29 — расписки в группе

В проде один групповой чат: «111», 5 участников, 3 сообщения. Правки
делались по нему, а не в вакууме.

**B28 — `readBy` оказался мёртвым полем, а не полем с неверной
семантикой.** Сплошная проверка (приложение, функции, правила) даёт
одного писателя — `markChatAsReadBy` — и **ни одного читателя**. Чинить
семантику было нечего: поле убрано из кода, из перечисления в
`firestore.rules` и из данных двух документов, где оно лежало (принцип
I4). Значения перед удалением сохранены в реестре: они подтверждают
диагноз — это был просто список всех, кто когда-либо открывал чат:

```
chats/1IBr5oq…_6s4Ffvk…   readBy = ["6s4Ffvk…", "1IBr5oq…"]
chats/KHgfvy6IUdBzty1Zz6Jn readBy = ["6s4Ffvk…"]
```

Побочно это стало первой боевой проверкой сторожа `[chat-write]`: обе
уборки видны в логе как `readBy` — не на пробном документе, а на
настоящих чатах.

**B29 — галочки показывали случайного человека.** Источником был
`members.firstWhere((m) => m != currentUid)`: в диалоге это ровно
собеседник, а в группе — первый попавшийся элемент массива. То есть две
синие галочки под сообщением в группе означали «кто-то один прочитал», и
кто именно — зависело от порядка `members`.

Теперь `deliveryStatusFor` принимает **список** остальных участников, и
семантика одинакова для диалога и группы: две синие — прочитали все, две
серые — доставлено всем, одна — кто-то ещё не получил. «Доставлено»
считается как «есть отметка ИЛИ уже прочитано», иначе старые документы
без `deliveredTo` откатывали бы группу с двух галочек на одну. Тем же
изменением закрыт и статус «прослушано» у голосовых — он брал того же
случайного участника.

Экран «Məlumat» в группе переписан на построчный список: разделы
«Oxudu» / «Çatdırıldı» / «Gözləyir» с именем, эмодзи и временем каждого.
Свести их в агрегат было нельзя — вопрос, ради которого этот экран
открывают, звучит как «кто именно прочитал».

Закреплено 16 тестами (`test/delivery_status_test.dart`), из них шесть —
на то, что **диалог ведёт себя ровно как раньше**, и один на то, что
порядок участников больше ни на что не влияет.

**Проверка на устройстве 02.08** (Teymur, боевая сборка), все четыре
пункта подтверждены пользователем:

| Проверка | Итог |

| Диалог: галочки под своими сообщениями не изменились | ✅ |

### N23 — карточка договора не обновляется в реальном времени 🟡

доходит до базы и сохраняется верно, но **на экране остаётся прежнее

себя обновить после сохранения, есть и намеренно оставлено пустым.

**Это не регрессия 03.08.** В этом файле правкой пункта 2 тронуты только

### Подсветка чужой правки — следствие N23, сделана следом

Живое обновление породило свою беду: чужая правка приезжает в открытую
карточку и **молча** подменяет значение. Человек смотрит на экран, дата
меняется — моргнул, и он не узнает, что договор трогали, и продолжит
помнить старую. Живое обновление без признака хуже устаревшего экрана:
устаревший хотя бы честно показывает одно и то же.

Изменившиеся строки заливаются золотым на 4 секунды и гаснут плавно
(`AnimatedContainer`, 600 мс). Заливка, а не мигание: мигание в столбце
из пяти строк читается как сбой отрисовки.

**Подсвечивается только чужое.** Своё сохранение человек только что сделал
руками. Важнее другое: признак, который загорается всегда, перестают
замечать за неделю — и тогда он не сработает там, где нужен.

**Как отличается своё от чужого — и почему первый вариант был неверен.**
Сначала лист возвращал записанные значения результатом маршрута, и
карточка сравнивала с ними. Это гонка: Firestore отдаёт локальную запись
в поток **немедленно, из кеша**, не дожидаясь сервера, — эмиссия
приходит раньше, чем лист успевает закрыться, и своя же правка
подсвечивалась бы. Поэтому лист объявляет, что собирается записать, **до**
записи (`onWillSave`), а не после.

Сравнение идёт **по значению, а не по флагу** «я только что сохранял».
Флаг проглотил бы чужую правку, случившуюся в ту же секунду; совпадение
значения — нет. Своё сохранение засчитывается ровно один раз: следующее
изменение тех же полей уже чужое.

**Ключи — имена полей, а не подписи строк.** У двух карточек подписи
разные («Vaxt» против «Saat», «Əlavələr» против «Qeyd»), и ключ по
подписи молча перестал бы совпадать на второй.

`onWillSave` — второй заход на колбэк в этом же файле после удалённого
`onSaved`. Разница ровно в том, за что `onSaved` и удалили: у этого
читатель есть. Если читателей станет ноль — удалять так же.

подметалка здесь не заплатка от лени, а более дешёвая форма той же
работы; цена ей — до суток лишнего хранения.

второго накопителя — «надгробие живёт вечно, файл вместе с ним» — на
данных не видно. Он остаётся возможным теоретически (таймер клиентский,
чат, который никто не откроет, надгробие не добьёт), но копится не он.

### Цена дыры B11-source — посчитана 03.08, вместо «до суток хранения»

**Скорость образования.** Поправка к прежней записи: 3 сироты медиа чата
были датированы **31.07 и 01.08**, а не «за две недели» — то есть за ~2
суток, и это меняет оценку в семь раз. Двое, удалённые 03.08, — не новая
порция: они созданы 01.08 в 20:03 и 22:17 и в прогонах 02.08 значились
как `skippedTooYoung: 2`, потому что им не было суток. Итого **5 сирот за
~2 суток плотного тестирования медиа**, ≈2.9 МБ. Контрольный отчётный
прогон 03.08 днём: **0 сирот, 0 моложе окна, 44 объекта — все со
ссылками**. То есть двое суток обычной работы (без тестов медиа) дают
ноль.

Честная величина — не «столько-то в день», а доля: ~5 сирот на ~45
медиа-загрузок того окна, примерно **одна на девять**, причём в период,
когда сообщения удаляли нарочно. Для сравнения: сироты статусов
(35 объектов / 110 МБ) образовались 14–23.07 и после 23.07 не
образуются вовсе — объём давала именно нарезка сегментов, а не чаты.

**Масштабирование.** Линейно по числу медиа-загрузок, а не по числу
пользователей самому по себе. При 1000 пользователей и 5 медиа в день на
каждого — 5000 загрузок, при доле даже 1/50 это ~100 сирот в сутки,
20–60 МБ. Лишние сутки хранения 60 МБ = 0.06 ГБ × $0.026/ГБ/мес ≈
**$0.00005 в сутки**. Вывод жёсткий: **деньгами окно ожидания не стоит
ничего ни на каком правдоподобном масштабе.** Цена дыры не в хранении.

**Почасовой прогон — считали, решили не делать.** Три причины, вторая
решающая:

1. *Стоимость.* Сегодня обход — 866 чтений, 24 прогона = 20.8 тыс.
   чтений в сутки ≈ $0.37/мес, и это внутри бесплатной квоты. Дёшево.
   Но обход по построению O(вся база): при базе в полмиллиона
   документов почасовой режим — это 12 млн чтений в сутки, порядка
   $200–400/мес против $9–18 при суточном. Дорожает не сама настройка, а
   форма — умножаем на 24 то, что и так растёт линейно с проектом.
2. *Выигрыш не 24-кратный, а полуторный.* Жизнь сироты =
   окно ожидания (24 ч) + ожидание ближайшего прогона (0–24 ч).
   Почасовой режим сокращает только второе слагаемое: средняя жизнь
   36 ч → 24.5 ч. Чтобы получить 24×, надо резать **окно ожидания**, а
   не расписание.
3. *А вот резать окно ожидания нельзя, и это не осторожность.*
   `attemptSendPendingMessage` (`background_queue_processor.dart:78`)
   **сохраняет `uploadedUrl` и при повторе не перезаливает файл**. После
   8 неудачных попыток запись паркуется со статусом `'failed'` — с
   сохранённым URL, до ручного повтора, который может случиться через
   сутки и через неделю. При окне в час сборщик снёс бы этот файл, а
   отложенный повтор записал бы сообщение со ссылкой на удалённый
   объект: битое медиа, молча и невосстановимо (локальная копия видео
   удаляется сразу после заливки, а iOS чистит temp). Двадцать четыре
   часа здесь закрывают не «разрыв в секунды», а офлайн-ретрай.

### Запрет: окно ожидания сборщика сирот сужать нельзя

Вынесено отдельно от расчёта выше намеренно. Это ровно тот вид запрета,
который через полгода снимут ради экономии, если причина не лежит рядом
с числом — а число выглядит щедрым и просится вниз.

`DEFAULT_MIN_AGE_MS = 24 ч` (`functions/src/orphanSweep.ts`) — **не запас
поверх разрыва в секунды**, как утверждала прежняя редакция комментария
там же. Комментарий был опасен сам по себе: «реальный разрыв — секунды,
сутки взяты на порядки больше» верно только для удачной отправки, и на
одной этой фразе час выглядит совершенно безопасным — он ведь всё ещё в
десятки раз больше секунд.

**Настоящий разрыв не ограничен.** `attemptSendPendingMessage`
(`background_queue_processor.dart`) при повторе **не перезаливает файл**:
он сохраняет `uploadedUrl` и переиспользует его — это сделано против
дублирующей заливки и гонки двух попыток за один `messageId`. После
`pendingQueueMaxAttempts = 8` неудач запись паркуется со статусом
`'failed'`, с сохранённым URL, и ждёт **ручного** повтора. Он может
прийти через сутки, через неделю, не прийти вовсе.

Значит между заливкой файла и появлением документа законно проходит
столько времени, сколько человек не открывал приложение. При окне в час
сборщик снёс бы файл припаркованной отправки, а отложенный повтор записал
бы сообщение со ссылкой на удалённый объект: **битое медиа, молча и
невосстановимо** — локальная копия видео удаляется сразу после заливки, а
iOS чистит temp.

Сутки — это граница, за которой ручной повтор уже маловероятен, а не
округление вверх от секунд. Комментарий у константы переписан под это же
обоснование: правило, у которого причина живёт только в реестре,
снимается при первом же чтении кода.

**Экономить при этом нечего** — см. расчёт выше: лишние сутки хранения
стоят порядка $0.00005 в день даже на тысяче пользователей.

### Задача: заметить, что сборщик тихо перестал ходить

**Это и есть настоящий риск**, а не размер окна. Именно так медиа
статусов дошло до 69% всего Storage: чистилка существовала, вызывалась,
в логах присутствовала — и просто не доставала до этих объектов.
Накопление шло молча, и увидели его только когда пошли считать байты
руками.

Сейчас незамеченная остановка выглядит точно так же, как исправная
работа: никто не смотрит в `maintenance/orphanSweep/runs`, пока не
случится повод. Проверять надо **наличие записей, а не частоту прогонов**
— частота задана расписанием и сама по себе ничего не подтверждает.

**Вариант решения** (не делать сейчас, записано как задача): одна
`onSchedule`-функция раз в сутки, дешевле некуда — читает последнюю
запись из `maintenance/orphanSweep/runs` и из
`maintenance/pushTokenSweep/runs` по `startedAt desc limit 1`. Если
свежей записи нет более N суток (N = 3: два пропущенных прогона подряд —
уже не случайность), пишет `logger.error` и шлёт push владельцу проекта
тем же механизмом, что и остальные уведомления. Два чтения в сутки,
никакого обхода. Заодно закрывает и сам сторож: если перестанет ходить
он, это будет видно по отсутствию его собственных записей — но проверять
сторожа сторожем незачем, достаточно чтобы ошибка попадала в Cloud
Logging, где на неё можно повесить алерт.

Существенная деталь: проверять надо **отдельно по каждому сборщику**, а
не «хоть какая-то запись есть». Они запускаются врозь (04:20 и 04:35) и
ломаться могут независимо.

### N25-push: что проверить в день включения APNs — по шагам

Записано пошагово, а не «проверить уведомления», по той же причине, что и
у N19-push: общая формулировка проверяется взглядом и закрывается ложно.
Каждая строка — отдельное действие с отдельным ожидаемым результатом.

**Условие для всех:** приложение на телефоне получателя **свёрнуто или
закрыто** (иначе сработает подавление присутствием и push не придёт — это
не дефект, а требование ниже, №12).

| # | Что сделать | Кто должен получить | Заголовок | По тапу |
|---|---|---|---|---|
| 1 | Владелец меняет дату мероприятия с двумя участниками | второй участник | `Tədbir dəyişdi`, тело называет **новую** дату | карточка мероприятия |
| 2 | Владелец меняет место | второй участник | `Tədbir dəyişdi` / «məkanı dəyişdi: …» | карточка |
| 3 | Владелец меняет форму одежды или заметки | второй участник | `Tədbir dəyişdi` / «qeydləri dəyişdi» | карточка |
| 4 | Владелец меняет дату И место одной правкой | второй участник | **одно** уведомление «tədbir məlumatlarını dəyişdi», не два | карточка |
| 5 | Владелец добавляет участника | только добавленный | `Tədbirə əlavə olundunuz` | карточка |
| 6 | Владелец убирает участника | только убранный | `Tədbirdən çıxarıldınız` | **список** «Müqavilələr» — карточка ему уже не читается по правилам |
| 7 | Владелец удаляет мероприятие | все участники | `Tədbir silindi`, дата в тексте | **список** |
| 8 | Участник выходит из чужого мероприятия («Əvəz et» на чужом) | **только владелец** | `İştirakçı ayrıldı` | карточка |
| 9 | «Əvəz et» на своём мероприятии | участники | **одно** `Tədbir əvəz edildi`, НЕ пара «silindi» + «əlavə olundunuz» | **новая** карточка |
| 10 | Отмена по согласию: сторона предлагает отмену | вторая сторона | `Ləğv təklifi` | карточка |
| 11 | Отмена по согласию: вторая сторона подтверждает | тот, кто предлагал | `Müqavilə ləğv edildi` | карточка |
| 12 | Напоминание за сутки и за 3 часа | все участники, включая владельца | `Sabah tədbiriniz var` / `Tədbirə 3 saat qaldı` | карточка |

**Отдельно — четыре проверки «не должно прийти».** Они важнее двенадцати
выше: лишний push человек заметит и пожалуется, потерянный не заметит
никто, но и обратное верно — push, пришедший не тому, виден сразу.

| # | Что сделать | Что должно произойти |
|---|---|---|
| A | Автор действия смотрит на свой телефон после любой правки | **ничего не приходит** — себе не уведомляем |
| B | Получатель держит **открытой карточку этого мероприятия**, автор правит дату | **push не приходит** (подавление присутствием), значение на экране меняется само |
| C | Получатель держит открытой карточку **другого** мероприятия | push **приходит** — подавление адресное |
| D | Владелец единственный участник, правит своё мероприятие | **ничего не приходит** никому |

**Что уже доказано машинно 03.08 и перепроверять не нужно:** срабатывание
триггера на нужное изменение (виден в логе эмулятора вызов
`onPersonalEventCreated` с правильным получателем и заголовком),
формирование текстов, выбор получателей, все четыре случая «не должно
отправиться» и идемпотентность. В день включения APNs проверяется **только
доставка и поведение на экране** — то, чего юнит-тест увидеть не может.

**Чем закрыт повтор доставки.** Cloud Functions гарантирует «хотя бы один
раз», то есть повтор при сбое — норма. Маркер кладётся в
`maintenance/eventNotifications/sent/{id события}` через `create()`:
второй раз он не создастся, и уведомление не уйдёт дважды. Маркер живёт в
отдельной коллекции, а НЕ в документе мероприятия — запись в него подняла
бы тот же триггер и породила уведомление о собственном уведомлении.

#### Уточнение 02.08: правило выше верно только для запросов по ОДНОЙ коллекции

Формулировка «под запрос из одних равенств индекс не нужен» оказалась
неполной и на этом чуть не подвела ещё раз. Проверено экспериментом при
работе над N20: запрос **по коллекции-группе** с одним-единственным
равенством

```
db.collectionGroup("pushTokens").where("token", "==", …)
```

падает с `FAILED_PRECONDITION: The query requires a COLLECTION_GROUP_ASC
index for collection pushTokens and field token`. Автоматические
одиночные индексы, на которых держится правило выше, заводятся **в
области COLLECTION**; область COLLECTION_GROUP автоматически не
создаётся никогда, сколько бы равенств в запросе ни было — хоть одно.

**Точная формулировка правила:**

| Запрос | Только равенства | Нужен ли индекс |
|---|---|---|
| по одной коллекции | да | нет, автоматических одиночных достаточно |
| по одной коллекции | есть `orderBy`/диапазон по другому полю | да, составной |
| **по коллекции-группе** | **да, хоть одно поле** | **да — одиночный с областью COLLECTION_GROUP** |

И вторая половина той же ловушки, уже описанная в I3 с другой стороны:
`fieldOverrides` для поля **заменяет** автоматическую индексацию
целиком, а не дополняет её. Поэтому в запись для `pushTokens.token`
внесены все три автоматических индекса (ASC, DESC, CONTAINS в области
COLLECTION) плюс нужный COLLECTION_GROUP ASC — ровно та же причина, по
которой это пришлось сделать для `statuses.expiresAt`.

Проверено после деплоя 02.08: TTL-политика осталась `ACTIVE`, три
индекса `expiresAt` — `READY`. `--force` не использовался.

**Применено 02.08.** Удалено точечно, по одному ID (`--force` не
использовался ни разу): 5 лишних из прода плюс два осиротевших из файла
и прода. Осталось по 4 с обеих сторон, все READY:
`chats: members + lastMessageTime desc`, `statuses: privacyMode +
expiresAt`, `messages: type + seq desc`, `statuses (CG): visibleToUids +
expiresAt`.

**Проверка после удаления** — прогнаны на проде все 19 живых форм
запросов приложения и функций, не только те, ради которых удалялись
